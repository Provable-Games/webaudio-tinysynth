## 2. Behavior as implemented

**Leading rest (D-023 item 2).** `playMIDI()` keeps the rest before the song's first event when `loopEnd > 0` and the transport stands at tick 0 of a pass with nothing of that pass sent yet: after `loadMIDI()`, after `locateMIDI(tick)` with `tick ≤ 0` (or not a number above 0), on the replay of a completed song (which is `locateMIDI(0)` plus play, D-005), after a loop wrap, and after a stop before the pass's first event. Tick 0 then sounds at `currentTime + 0.1 s`, and the first event at its own tick's time, timed at 120 BPM (no tempo event can precede the first event). Later passes keep the existing `loopEnd` wrap timing unchanged.

Unchanged: with `loopEnd` unset (0), the first event plays at `currentTime + 0.1 s` exactly as upstream, so the differential, tempo and loop-end regressions pass unchanged with identical traces. A seek to any tick above 0, including one inside the leading rest, keeps next-event positioning (D-005): the next event plays 0.1 s after `playMIDI()`. A stop after the pass's first event resumes at the next event, as before.

Why one line in `locateMIDI`: only `locateMIDI` knows the requested tick. After `locateMIDI(0)` and `locateMIDI(48)` on a song whose first event is at tick 96, the transport state is identical (`playIndex 0`, `curTick 96`). Treating both as tick 0 would give the seek to 48 the whole leading rest, which is neither next-event nor requested-tick positioning (mutant M2). It sets `_z = !(tick > 0)`; the wrap sets `_z = 1`, so a stop in a later pass's leading rest behaves the same whether pass 1 began from a load or a seek (mutant M3).

**`getPlayStatus().startTime` (D-023 item 3).** The AudioContext time at which tick 0 of the current pass sounds. With `loopEnd` set, every event at tick T of any pass sounds at `startTime + seconds(0 → T)` under the song's tempo map (120 BPM until its first tempo event). With `loopEnd` unset this holds in the first pass only; later passes are covered in the wrap item below (review F1).
- Fresh play from tick 0 with `loopEnd > 0`: exactly `currentTime + 0.1`, when tick 0 sounds.
- `loopEnd` unset, after a seek, or on a resume: the next event plays at `currentTime + 0.1`, and `startTime = currentTime + 0.1 − seconds(0 → curTick)`: the virtual tick-0 time of the resumed position. It can be in the past. `seconds(0 → curTick)` follows the pass's tempo map. That is the song's map from 120 BPM, except that a pass the default loop started opens at the tempo it inherited (`_x0`, set at the wrap). A resume inside such a pass therefore uses the tempo it actually plays at (PR #39 Codex review), and `locateMIDI` clears `_x0`, so a seek uses the song's map.
- At each wrap it moves on. With `loopEnd`, it is the padded end of the previous pass (the next pass's real tick 0). With the default loop, it is `time of the next pass's first event − firstTick × the current seconds per tick`. That pass keeps the previous pass's final tempo until its first tempo event (upstream), so the value is extrapolated at that tempo.
- It follows the scheduler, as `curTick` does. It moves to the next pass when the current pass's last event is scheduled: up to 0.2 s before that event sounds, plus any rest up to `loopEnd`. So it can be later than `currentTime`.
- It is `null` when not playing: no song, loaded but not started, after `stopMIDI()`, at the song's end, after a load, after `dispose()`, and on an offline context.
- It is an ordinary fourth field: `getPlayStatus()` returns `{play, maxTick, curTick, startTime}`, and `JSON.stringify()`, spread and `Object.keys()` carry it. This additive shape change is deliberate (supervisor decision, §4).

## 8. Residuals

- `startTime` follows the scheduler, not the audio output (§2). This matches `curTick`, and it lets a caller see the next pass's start ahead of time. The consumer reads it once after `playMIDI()`, so it is unaffected.
- With `loopEnd` unset, later passes inherit the previous pass's final tempo until their first tempo event (upstream behavior). There, `startTime` is extrapolated at the inherited tempo, at the wrap and on a resume, which matches how the pass plays. Events after the pass's first tempo event follow the song's map from that inherited opening, not from 120 BPM. `loopEnd` is the documented path for exact looping.
- A context replaced mid-play does not rebase the clock (pre-existing, D-025 F8). `startTime` stays on the old timeline until the next `playMIDI()`.
- Merged `improve/integration` `a6d3f0e` (T4, T9-D) at `26483c2` (rule 6). Only min.js and its map conflicted. The integrated tests add no three-field status assertion: `tests/browser/specs/demos.js` reads status fields one by one. Branches that merge after this one adapt their own shape assertions with `H.playStatus`.
- Contract ledger L-14 (supervisor-owned) still cites `76a4a12`, the superseded non-enumerable candidate (review F5).

**NOTICE** (new bullet after the transport bullet):

```
  - webaudio-tinysynth.js: with loopEnd set, the first pass of a song
    started from tick 0 keeps the rest before its first event, as later
    passes already did, and getPlayStatus() has a startTime: the
    AudioContext time at which tick 0 of the current pass sounds.
```

**README, "What behaves differently"** (new sub-bullet under "Playback no longer hangs or depends on what happened before"):

```
  - With `loopEnd` set, the first pass keeps the rest before the song's first event, as every later pass already did: `playMIDI()` from the start (after `loadMIDI()` or `locateMIDI(0)`, or on a finished song) sounds tick 0 0.1 s later and each event at its own tick's time. Upstream, and this fork with `loopEnd` unset, plays the first event at once. A seek to a later tick still resumes at the next event.
```

**README, "What is added"** (append): `getPlayStatus()` has a fourth field, `startTime`: when tick 0 of the current pass sounds, for syncing visuals to the music.

**README, "What is unchanged"**: add `getPlayStatus` to the list of documented exceptions.

**README, `setLoopEnd()`** (append to the "Timing:" paragraph): `The first pass keeps that rest too when it starts from tick 0 (after loadMIDI(), locateMIDI(0), or on a finished song).`

**README, `getPlayStatus()`** (replace the entry):

```
**getPlayStatus()**
> get current MIDI sequence play status.
> return value is a object `{play:playstatus, maxTick:maxtick, curTick:currenttick, startTime:time}`. `startTime` is new in this fork.
> `startTime` is the AudioContext time at which tick 0 of the current pass sounds, or `null` when not playing. With `loopEnd` set, an event at tick T of any pass sounds at `startTime` plus the time from tick 0 to T under the song's tempo map (120 BPM until its first tempo event). With `loopEnd` unset this holds only in the first pass: a later pass keeps the tempo the previous one ended on until its first tempo event (as upstream), so `startTime` is extrapolated at that tempo. Use `loopEnd` for exact sync. With `loopEnd` set and play from tick 0, tick 0 sounds 0.1 s after `playMIDI()`. Otherwise (`loopEnd` unset, after a seek or a resume) the next event plays 0.1 s after `playMIDI()`, and `startTime` is when tick 0 would have sounded, which can be in the past. Like `curTick`, it moves to the next pass when the sequencer reaches the end of the current one, up to 0.2 s before the last event sounds and before any rest up to `loopEnd`, so it can be later than `currentTime`: while it is, the previous pass is still sounding.
> To start visuals with the music: `const st = synth.getPlayStatus().startTime; setTimeout(start, (st - ctx.currentTime + (ctx.outputLatency || 0)) * 1000);`
```
