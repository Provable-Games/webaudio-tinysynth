## 1. Outcome

Three changes, each justified by a measurement, in three commits; the data of every buffer is byte-identical for every seed (`bufferVersion` stays 1), and nothing global is cached.

| Change | What it removes | Measured gain |
| --- | --- | --- |
| `noiseBuf.n1` is generated when first read | 64 passes of sine products (2.8 M `Math.sin` calls) from every install | 41–45 ms of a 43–49 ms install in Chromium 153; construct + first melodic note 44–50 ms to 2.3–5.2 ms warm, 55–62 ms to 9–14 ms cold. It is paid once per context installation, by the first `playMIDI()`, by `prewarm()` or by the first note that plays `n1` (§5). |
| No reverb impulse with `useReverb: 0` | the half-second stereo `convBuf` and its loop | 0.4–0.5 ms warm (about 1 %), about 2 ms cold, and half of the install's buffer memory (344.5 to 172.3 KiB at 44.1 kHz). |
| One `setQuality` in the constructor | the quality-1 install before `setQuality(q)` | the constructor's own cold time 6.8–7.5 ms to 2.0–2.6 ms; warm 0.2–0.4 ms; less code. |

Rejected, with numbers (§6): a lazy `n0`, an inlined generator, a copy-only `setQuality` or shared timbre tables, idle-time prefetch of `n1`, and a lazily created `n1` buffer.

## 2. Method

`scripts/bench-init.js` (`npm run bench -- node|browser`, header documents every option). It instruments a copy of the library (a `__t8m(label)` call before a few statements of `setAudioContext()`), minifies that copy with the pinned build options, and loads it in a page served from an ephemeral 127.0.0.1 port with COOP/COEP headers (`crossOriginIsolated`, so `performance.now()` resolves to 5 µs in Chromium and 20 µs in Firefox and WebKit). `--src` measures another copy, so the base (`git show 2f82ec7:webaudio-tinysynth.js`) and the candidate go through the same build and the same code path. For each quality (0, 1), `useReverb` (0, 1) and sample rate (44100, 48000), on an `OfflineAudioContext` created before the timer starts:

- **cold**: a fresh browser context and page per sample (12 samples), one construction `new WebAudioTinySynth({context, quality, useReverb})`, split into the constructor's own work and `setAudioContext()` segments, then the first melodic note (program 0), the first `n0` note, the first `n1` note (program 119) and a second one;
- **warm**: the same 20 times in one page after 3 untimed runs, plus a lazy constructor and `setQuality(q)` alone;
- **graph**: nodes and buffer bytes created (a count of every `create*` call);
- **dense chord**: 60 melodic voices on 15 channels and 12 drum hits (64 voices allowed), scheduled on a 2 s offline context, five times: construction, a read of `noiseBuf.n1` (so the lazy build's generation is not counted in the schedule time), the JS time to schedule, and `startRendering()`;
- Chromium also times the realtime default path, `new WebAudioTinySynth()` with its own `AudioContext`.

Two discarded rounds in fresh pages per engine absorb the browser process's start-up (the first run of the first configuration read slow without it). The Node mode runs the mock WebAudio of `tests/harness.js` in the main V8 context (the harness's `vm` contexts run `Math.sin` about 15 times slower) and is for breakdowns only: the mock does no audio. All three engines ran under `heavy-run.sh` (rule 11).

## 3. Where the time goes (base, Chromium 153, warm, `q1 rev1 44.1k`)

The base install is 45 ms. `n1` is 41.0 ms of it (91 %); the reverb impulse 0.42 ms; `n0` 0.14 ms; the channel setup 1.1 ms (16 channels' nodes); `reset` 0.45 ms; the convolver with its buffer 1.9 ms (native, reverb on only); the constructor's own work (`setQuality` twice) 0.8 ms. In Node on the mock: 28 ms of 30 ms (`n1` 27.7 to 30.3 ms), `convBuf` 0.26–0.5 ms, `n0` 0.09–0.1 ms. At 48 kHz `n1` costs 44.6 ms (the buffer is 9 % longer). In a cold page, the first loop that runs also pays the interpreter: 1.8 to 5.5 ms for the first noise buffer, which moves to `n0` when the impulse is skipped (cold, `q0 rev0`: impulse 1.75 ms and `n0` 1.1 ms before; `n0` 4.5 ms after).

## 5. The first-use stall

With a lazy `n1` the cost moves to the first need: a live note that plays `n1` (a cymbal, a hi-hat, programs such as 119 Reverse Cymbal, or any custom timbre with `w: "n1"`): 41–47 ms in Chromium 153, 26–29 ms in Firefox 155, 20–29 ms in WebKit 26.6, on this machine and independent of quality, reverb and rate except the buffer length (44.1 to 48 kHz: 41 to 45 ms in Chromium). That is the same work the install did before, once per context installation (`setAudioContext()` with the same object builds fresh buffers). Every song pays it: the first `playMIDI()` builds it before it reads the clock (round 5, below), whatever the song holds, so there is no melodic-only saving to claim; the saving is that a synth that only constructs, or plays live notes without `n1`, does not pay it. A slower device scales it, as it would the install.

**Review findings (Codex, MEDIUM, both fixed in this PR).** *Round 1.* `noteOn()` took a note's onset from the clock and then `_note` read the lazy buffer, so a generation that advanced the audio clock left the first live note's envelope and stop times in the past: a 35 ms closed hi-hat (quality 1, drum 42) started and stopped before the clock, and could vanish. `noteOn()` now resolves the timbre's `n*` buffers first and only then reads the onset, so an immediate note starts after the generation with its full envelope: delayed by the generation time, once. *Round 2.* An explicit time that was the current time, or a lead shorter than the stall, was returned unchanged by `_tsConv` and ended up in the past the same way (`send([0x99, 42, 100], ctx.currentTime)`). `noteOn()` now moves a time that was current or future on entry (`t >= currentTime` before the generation) and is past after it to the clock, only when this call generated `n1` (the getter was still there before and is gone after). Times that remain in the future are as given, and a time already past on entry is as given, as without the lazy build; with `n1` generated, unused, or no stall, the calls to WebAudio are as before. The regression test advances the mock clock by 41 ms inside the first generation and, for no time, the current time, 1.02 s and 1.0409 s, requires a start at or after the new clock time and the pre-generated case's duration; a time 0.5 s ahead and a past time are unchanged. It fails without the first line, without the move, and with the move applied to past times (checked by mutation). *Round 3 (Codex MEDIUM, approved beyond the round limit by the coordinator).* Moving the onset made the matching note-off miss (`noteOff()` matched `t >= nt.t`): a first program-119 note whose onset and release both fell inside the window stayed sustained. A voice now keeps the time it was asked for (`nt.s`, set by `noteOn()` only when it moved the onset), `noteOff()` and the pedal-up match against it, and release at `max(t, nt.t)` so no AudioParam event precedes the onset. Tests (both builds): the Codex case (onset 1.01 s, release 1.03 s, 41 ms stall), a note-off exactly at the moved onset and one after it, the pedal held across the window and lifted inside it, exactly at the onset and after, a note-off before the requested time still not matching, and `allSoundOff()` and `stopMIDI()` inside the window; every release event is at or after the moved onset and none has a negative value. The requested time is taken before the generation, so a note with no time (`undefined`, `null` or 0) is asked for at the entry clock, and its timed note-off and pedal-up inside the window match too (a fourth Codex finding on this fix: the first version captured it after the generation); the test covers those three forms with and without the pedal. Mutants: `nt.s` not kept, the `max` clamp removed, and the requested time taken after the generation all fail it.

*Realtime measurement* (`_evidence/t8-perf/realtime-onset.js`, Chromium 153, real `AudioContext`, `noteOn(9, 42, 100)` with no time, 8 fresh pages): the first call takes 42.6–44.6 ms (median 43.1) and the note's `start` is 46.4 ms after the call's entry time in the six runs where the audio clock had moved (in two it read 0 because the clock had not advanced on the page's first quanta, the call time is the same); the second call takes 0.1 ms and starts at once. So the first live `n1` note sounds about 46 ms late, once per context; stated in the README.

A note whose time has already passed when the generation ends is late by that much, as after any long task. The sequencer is the exception that needed its own fix (round 5). A caller that wants no delay at all calls `prewarm()` after `resume()` (round 5).

*Round 5: sequenced playback (external review, GPT-6.1; design agreed with the user's reviewer).* Rounds 1–4 protect a note sent while it is being built, but a song whose first beat holds a piano, a hi-hat and a snare was audibly flammed: `playMIDI()` sets the start at `currentTime + 0.1`, the scheduler's first callback can come later than the 0.1 s lead minus the build, and the hi-hat's `noteOn` then built `n1` inside the callback, so the hi-hat moved to the new clock while the notes sent with it did not. The mock reproduces it with the first callback 70 ms late and a 41 ms build: onsets 1.100 s for five sources and 1.111 s for the hi-hat (an 11 ms flam; the review saw 100 ms against 107 ms). The fix, as agreed: `playMIDI()` calls the new public `prewarm()` straight after its eligibility checks (offline rejected, no song or only tempo events returns) and before the completed-song reset, the controller restoration, the dummy oscillator and `a = currentTime + 0.1`, unconditionally (no inspection of the song). The clock is read after the build, so the whole song shifts equally and `startTime` stays exact: with the same test, all six sources start at 1.141 s (the clock the build left, plus 0.1 s) and their envelope lengths equal those of the pre-built case, whose onsets are 1.100 s. A first `playMIDI()` per installation therefore waits the build (20–47 ms on a desktop) before it sets the start: the song starts slightly later and nothing within it shifts.

`prewarm()` is `if(!this._dead && this.actx && this.noiseBuf) this.noiseBuf.n1;`: synchronous, returns `undefined`, plays nothing, creates or resumes no context, is a no-op before a context exists, after `dispose()`, and when `n1` is built. Live callers use `await synth.resume(); synth.prewarm();`; without it the first live `n1` note is about 46 ms late (realtime measurement above), with its envelope intact (rounds 1–4). It removes this deferred generation only, not other first-use or scheduling costs. Tests (both builds, `tests/unit/init-cost.test.mjs`): the same-tick piano, hi-hat and snare through `playMIDI()` with the first callback late and the clock advancing 41 ms in the build (one onset, full envelopes, `startTime` exact); `stopMIDI()` then `playMIDI()` and `locateMIDI()` then `playMIDI()` (the clock is read after the build); a second play, a loop wrap and a seek while playing build nothing more; `stopMIDI()` then `setAudioContext()` with a new or the same context object then `playMIDI()` (rebuilt for the new installation, before the clock; the install itself builds nothing); rejected offline playback, a missing song and a tempo-only song build nothing; with `loopEnd` set tick 0 sounds 0.1 s after the build and the first event 0.5 s later, `startTime` exact; `prewarm()` before a context exists, after `dispose()`, twice in a row and after `resume()`, and the next live note starts exactly on time. Mutants: no `playMIDI()` pre-read fails 5 tests; a no-op `prewarm()` 6; the call placed before the eligibility checks (offline, no song) 2.

*Codex LOW on round 5.* `noteOn()` set `s` on the last voice in `notetab` after `_note`, which a dropped note (here a custom `n1` timbre whose pitch overflows float32, after the build) left as an earlier voice with the same onset, so a later note-off before that voice's onset released it. `_note()` now returns the voice it makes (none when it drops the note, and for percussion) and `noteOn()` sets `s` on that object only. Regression test: a valid voice at 1.041 s, a dropped note at 1.01 s moved to 1.041 s by a 41 ms build, a note-off at 1.03 s: the voice keeps `s` and stays held, as in the base; the old code fails it.

*Real Chromium 153* (`_evidence/t8-perf/realtime-flam.js`, real `AudioContext`, the same song, 8 fresh pages each): on an idle page the first scheduler callback comes early enough that even without the pre-read the onsets are identical (spread 0.0 ms, first onset 100 ms after the `playMIDI()` call), so the flam needs a late first callback (a busy page, as the review had) and the mock's 70 ms stands for it. With the pre-read the onsets are identical too (spread 0.0 ms) and the first one is 146 ms after the call in 6 of 8 pages (100 ms in the other two, where the audio clock had not advanced when read): the song starts about 46 ms later, the measured cost of the build. Nothing within the song shifts.

*A lazy synth reaching `playMIDI()` with no context does not exist:* `_live()`, the first statement of `playMIDI()`, creates the internal context for a lazy synth (as it does for `loadMIDI()` and every other method), so `prewarm()` always sees one there; a test pins that a lazy `playMIDI()` creates the context itself and, with no song, builds nothing.

The README keeps its requirement to call `stopMIDI()` before replacing the context, and now says the cost is once per installation.

Custom noise timbres in quality 0 use the same path: `setTimbre(0, 0, [{w: "n1"}])` plays the seeded data on its first note (`tests/unit/init-cost.test.mjs`). Registered waves (`setSampleWave`, `setHarmonicWave`) never read `n1`; the registry (`_wv`) keeps tables, not buffers, so it holds no context.

## 6. Decisions: built, and rejected with numbers

**Built.** (a) Lazy `n1`: `lazyN1(o, b, g)` at module level defines `o.n1` as an enumerable accessor that fills buffer `b` from generator `g` (stream 2) on first read and then redefines `n1` as a writable data property; an assignment before the read does the same without generating. It closes over the buffer and the generator only, never the synth or its context, so a disposed or replaced synth that never read it retains nothing and does no work. `Object.keys(noiseBuf)` is still `["n0", "n1"]` (listing the keys generates nothing; `Object.entries` reads it). (b) `useReverb` guards the impulse and sets `convBuf` to `null` otherwise (a first install used to leave it `undefined`, a reinstall `null`); `useReverb` is read at each install, as the convolver always was, so toggling the property and installing again adds or drops it. (c) The constructor destructures its options and calls `setQuality(q)` once; `undefined` and `null` install quality 1, as the old `setQuality(1)` did, and an invalid quality throws before any context exists.

**Rejected.**

| Candidate | Evidence | Why not |
| --- | --- | --- |
| Lazy `n0` too | `n0` is 0.09–0.3 ms warm (0.14 ms in Chromium); 1.1–4.5 ms cold, which is the first loop's interpreter cost | Almost all drums play `n0`, so the cost would move, not go away, and it would add a second accessor. |
| Inline the generator in the `n0` loop | A variant (`vb.js` in the evidence) measured 9.7 ms cold against 9.2 ms without it | No gain: the cold cost is the first loop's warm-up, not the closure call. |
| Copy-only `setQuality` for the built-ins, or timbre data shared between instances (T5 §16 F8) | `setQuality(q)` is now 0.15 ms (q0) and 0.37–0.5 ms (q1) warm, 0.7–1.4 ms cold, at most 14 % of the cold readiness time; a lazy synth keeps 270 (q0) to 420 (q1) KiB of heap in Node | A copy-only path would skip `_op`'s validation of tables a caller edited (`program0`, `program1` and the drum tables are properties) and share objects that L-09 promises are copies. The gain does not justify weakening that contract. Revisit with T7. |
| Idle-time or chunked generation of `n1` | Needs a timer per synth, state for offline contexts (which render at once and need it synchronously), and a lifecycle path in `dispose` | The lazy read is exact and has no timers. The pre-warm is one read for a caller who wants it. |
| Create the `n1` buffer lazily too | The unfilled buffer is 86–94 KiB, 0.02 ms | The accessor would need the context (`createBuffer`), keeping a disposed context reachable from a held `noiseBuf`. |
| A faster `n1` algorithm | 2.8 M `Math.sin` calls at about 14 ns each | Any change to the arithmetic or the float32 accumulation order changes the bytes (version 1 data is fixed). Not attempted. |
| AudioWorklet or WASM | Out of scope (issue #18) | Measured need does not call for it: the remaining install is 2–5 ms warm in Chromium, mostly native node creation. |

## 10. Notes for later

- `convBuf` is `null` with `useReverb: 0`; any code that read it must check. Nothing in this repository outside the seed tests and the render page's hash helper reads it (the demos do not), and the helper reports a missing buffer as `null`.
- A caller that wants the install work done up front (a loading screen, or before live notes) calls `synth.prewarm()` after `await synth.resume()` (round 5); reading `synth.noiseBuf.n1` does the same.
- With T7 (the module split, deferred by D-041) the buffer generation could become a shared pure function of `(seed, rate)` that returns Float32 data without a context; that would also let the unit tests skip the `vm` slowdown. Not needed now.
- The benchmark is reproducible: `npm run bench -- browser --src=BASEFILE --json=OUT` and the same for the candidate; `--engines=chromium` for a quick run (about 40 s).
