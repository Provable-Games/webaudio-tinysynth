## 2. Design

- **One declaration.** `tests/browser/matrix.js` lists engines, builds (`source` = `webaudio-tinysynth.js`, `min` = `webaudio-tinysynth.min.js`), quality modes (0, 1), sample rates (44100, 48000), the Math.random seed, deadlines and the specs with their kind and dimensions. The runner prints it before and with the results.
- **Runner.** `scripts/browser-matrix.js` runs the analysis self-test, then one worker process per engine under `scripts/run-with-deadline.js` (1200 s, process-group kill). Inside a worker every case has its own Node-side deadline (60 s default; render 600 s, hang 6 s): at the deadline the case fails, its pages and contexts are closed from Node, and a browser that does not respond is closed and relaunched. A browser that cannot launch fails the worker and the run ("NOT LAUNCHED"); nothing is skipped. The last line is `PASS:` or `FAIL:` (the `run-regressions.js` contract). `--source=PATH`/`--min=PATH` test another copy of a build; `--out=DIR` writes `results.json` and WAV renders; `--seed=N`; `--list`. `--engines=`/`--specs=` must name at least one entry, and a run or worker in which no case ran fails. Workers receive the orchestrator's normalized (absolute) arguments. With `GITHUB_STEP_SUMMARY` set it writes a result table.
- **Kinds.** `assert` specs (embed, render, gesture, url, lifecycle) run by default and fail on any failed check. `observe` specs (hang, variation; `npm run test:browser:observe`) record baseline behavior and fail only if an observation cannot be made. Assert specs also record observations (JSON) for behavior T2–T5 will change; no failing or skipped test was committed.
- **Controlled server.** `scripts/browser-server.js` (Node `http` only) on 127.0.0.1, ephemeral port, every request logged. Routes: library builds, registered pages, `/midi/ok|status/<code>|redirect|empty|garbage|truncated/<n>|reset|hold/<key>|slow/<ms>`. `hold`/`release` make races deterministic. CLI mode serves the repository read-only for manual listening (`npm run test:browser:serve`).
- **Test pages.** Built in Node (`tests/browser/lib/pages.js`): `page/prelude.js`, optional `page/instrument.js` and the inlined library in `<head>`; page scripts in `<body>`. Render and embed pages run offline (every request aborted); gesture, URL, lifecycle and hang pages are served over `http://127.0.0.1`.
- **Seed-aware infrastructure (test only).** The prelude replaces `Math.random` with a resettable mulberry32 stream before the library loads; `render()` restarts it before construction and again before `setAudioContext()`, so generated buffers depend only on (seed, sample rate). This is not runtime policy (D-004 is T8's). The seed is printed with every run and recorded in `results.json`; `render()` reports the hashes of `convBuf`, `n0` and `n1` and the number of random values drawn.
- **Offline renders.** `page/render.js` constructs the synth, installs an `OfflineAudioContext` with `setAudioContext()`, schedules every note and controller at explicit times and renders. It stops the constructor's 60 ms interval before rendering (handle captured by the prelude; the library does not expose it, #11), because that scheduler keeps pruning voices during an offline render at wall-clock-dependent positions (§4.4). PCM is returned as base64 Float32 and analyzed in Node (`tests/browser/lib/analysis.js`), so one implementation measures every engine.
- **Analysis.** Pitch: strongest peak within ±1.5 semitones of the expectation, Blackman-Harris window, ≥8× zero padding, quadratic interpolation of the log magnitude. Self-test on synthetic tones between FFT bins with harmonics and noise: error < 0.001 cents at 44.1 and 48 kHz. Vibrato: zero-crossing instantaneous frequency. Envelope: per-period amplitude of a 300 Hz tone (an integer period at both rates), crossing times, log-linear time-constant fits.

### 4.3 Deterministic data versus rendered-audio tolerance

- **Deterministic data.** With the test seed, `convBuf`, `n0` and `n1` hash identically in all three engines, both builds and every run, per sample rate (44.1 and 48 kHz differ, as D-004 expects). The library draws 66,238 values at 44.1 kHz and 72,038 at 48 kHz (seed `0x5eed0001`). No tolerance applies.
- **Same engine.** Firefox renders were bit-identical everywhere (sources, builds, launches). Chromium renders with three or more simultaneously sounding inputs into one node differ between runs by up to 1.9e-7 at test levels and 5.45e-5 after the compressor at the default level: Chromium sums a node's inputs in a run-dependent order. Reproduced without the library (an `OfflineAudioContext` with three oscillators into one gain: 3 distinct hashes in 8 runs; 2 inputs: 1; Firefox and WebKit: 1; `logs/summation-order.txt`). WebKit differs only in quality-1 drum sweeps (≤ 9.3e-8): the library's percussion `onended` handlers disconnect detune inputs while the render runs. Custom-timbre scenarios were bit-identical in all engines.
- **Across engines.** At the test level the engines agree within 0.085 dB on GM energies and exactly on the makeup gain. At the default `masterVol` 0.5 Firefox's DynamicsCompressor compresses harder: GM program energy up to 3.6 dB and loud drums up to 5.5 dB lower than Chromium and WebKit, which agree within 0.01 dB (`logs/compressor-gap.txt`). That was the 2.7 % Firefox RMS gap seen in the first probe; it is DSP, not generated data.
- **Across seeds** (noise-based sounds, same engine): drum energy varies by up to 1.5 dB (Chromium, WebKit) and 2.8 dB (Firefox), the reverb tail by 4.0 dB.

### 4.4 Findings from the renders (baseline, not fixed here)

1. **The scheduler acts on offline renders.** The 60 ms interval keeps running after `setAudioContext(OfflineAudioContext)`, and the context's `currentTime` advances while it renders, so released voices are pruned (cut from about 3 % amplitude) at positions that depend on wall-clock timing. With the interval left running, three renders of one GM batch differ by up to 3e-3 (−50 dBFS); stopped, they match (variation spec). #11 (handle, dispose) and #12 (defined OfflineAudioContext behavior) should cover this; the render infrastructure stops the interval meanwhile.
2. **Unhandled rejections with an OfflineAudioContext.** `send()` calls `resume()` on the not-yet-rendering offline context and leaves the rejection unhandled: 192 per render case in every engine (2 per install plus every `send()`). Closing the realtime context the constructor created rejects its pending `resume()` (Firefox "Closed before resume completed", WebKit "AudioDestinationNode is not initialized"; 88 per case). #12/T4.
3. **Peaks beyond full scale.** In quality 1 at the default `masterVol`, drums 49 and 55 peak at 1.157 (44.1 kHz) and 1.286 (48 kHz) in Chromium and WebKit (0.69 in Firefox). Recorded, not asserted.
4. **Pitch-bend unit.** The library maps bend range units to 100/127 cent; MIDI's RPN 0 gives 100/128. ±8191 at the default range is 201.55 cents (MIDI: 199.98), and a 12-semitone range gives 1209.30 cents (1199.85). The checks assert the library's established mapping and print the MIDI value beside it. No task owns this: supervisor decision.
5. **Short notes on slow-attack timbres are silent.** A note released before its attack ends renders nothing until note-off: `_releaseNote` calls `cancelScheduledValues(t)`, which removes the whole pending `linearRampToValueAtTime` (its end time is after `t`), so the gain stays at the attack's starting 0. With a 0.3 s note, GM 119 (Reverse Cymbal, a = 1 s) is silent in both qualities and GM 125 (Helicopter) in quality 1, in every engine (variation spec, `results/observe3`). The earlier sequential GM batch hid this: the previous program's tail sounded in their slots (§15). No task owns it: supervisor decision.

## 8. Hangs

Allocation-free baseline hangs under a 6 s case deadline, both builds, all engines: #4 ws.mid cut at 40 bytes through `loadMIDI()` and through `loadMIDIUrl()`; #8 a tick-0 tempo-only song with `setLoop(1)` (hangs even with a suspended context). ### GM 119 and 125 are silent on short notes (characterization only)

**Observed** (variation spec, §4.4.5). With a 0.3 s note at C4:
- GM 119 (Reverse Cymbal) is silent in both quality modes;
- GM 125 (Helicopter) is silent in quality 1.

Held 1.2 s, both are audible (peaks 0.23–0.50).

**Timbres.** Program 119 is `[{w:"n1",v:0.3,a:1,s:1,d:0.15,r:0,t:0.5}]` in both tables. Program 125 in quality 1 is `[{w:"n0",…,a:1,d:11,s:1,r:0.5},{w:"square",…,g:1}]`. Quality 0's 125 has no attack and sounds.

**Mechanism.**
1. `_note` starts the gain at 0 with `setValueAtTime(0,t)` and schedules `linearRampToValueAtTime(vp, t+a)`, with `a` = 1 s.
2. A note-off at T < t + a calls `cancelScheduledValues(T)` in `_releaseNote`. The ramp's event time t + a is after T, so the whole ramp is removed (Web Audio semantics) and the gain stays at 0 until T.
3. For 119, the release then sets the interpolated value and, with r = 0, `setValueAtTime(0, T)` at the same time, so the note is silent.
4. For 125 in quality 1, `t2` comes from the last operator (the modulator, a = 0), so no value is set at T, and the release decays from 0.

Any note on these timbres released before its 1 s attack ends is silent.

**Upstream.** `3d75aee` behaves identically:
- its `_note` ramp, `_releaseNote` and `t2` code are byte-for-byte the same, and both timbres are identical;
- rendering upstream's file with the same items gave the same peaks as the fork in all three engines: 0 or 2.3e-7 for 0.3 s notes, audible for 1.2 s notes (`logs/short-notes-upstream.txt`).

**Conclusion.** This is upstream behavior: the release cuts a long attack. No timbre or envelope change is in scope. The GM sweep holds notes 1.2 s, and the phase-B plan lists the short-note case for a supervisor decision.

### WebKit's occasional render differences

**What happens.** WebKit sometimes renders one part of a scenario differently from an otherwise identical render, with a single changed segment of up to 0.56.

**Frequency.**
- In normal runs, 2 differing parts appeared in about 13 full WebKit render runs (CI and local, about 1,900 renders each). That is roughly 1 in 12,000 renders:
  - CI on `ce9489d`: a q1 48 kHz drum;
  - a local merge run: program 127, q1 48 kHz.
- Under artificial main-thread GC pressure during rendering, it occurs about once in 40–60 renders.
- Chromium and Firefox have shown no such difference.
- The cause is not isolated:
  - the realtime internal context is not it (`a160e0b`);
  - the percussion `onended` handlers are not it (program 127 has none).

**Policy (`691ce5c`).** When source/min parity or the fresh-page repeat differs beyond the same-engine tolerance:
1. The differing part (one item, or the whole scenario for a single render) is re-rendered at most twice per side.
2. It is accepted only when a render of one side then agrees with a render of the other side within the tolerance. That agreeing pair is used for the measurements and WAV files.
3. At most 3 parts per case may be reconciled.
4. Every reconciliation is recorded with its part, size, first differing sample and render count (observation "reconciled same-engine differences").

**Why it cannot mask a deterministic defect.**
- A library or build defect is a function of the inputs. The same JS calls build the same graph, so the difference reproduces on every re-render, the two sides never agree, and the check fails with the first differing sample. Demonstrated: a glitch injected into every render of program 127 failed with "reproduced in 6 renders" (§15 round 2).
- Measurements always come from a pair of renders that agree. So a one-off render can neither pass nor fail a check on its own.
- A timing-dependent library defect that only rarely changes output would be reconciled. It would still appear in the recorded observations. The cap of 3 parts per case also turns a frequent one into a failure.

### 17.2 Design

- **Parser (`specs/parser.js`).** One case per input and build, each in a fresh page served from the controlled server, because a hung page cannot be reused. The page loads a 16-beat previous song, loops and plays it, and sets program 7 on channel 0. One synchronous page call then loads the input and compares the song object, `maxTick`, `curTick`, event count, play flag and program before and after. Node arms a 5 s deadline (`OP_DEADLINE`) around that call only. Inputs are built in Node; the expected song length and event count of the recoveries come from `lib/smf.js`.
- **Transport and seek (`specs/transport.js`, `specs/seek.js`).** Realtime contexts on served pages, as in the lifecycle spec. An offline, deterministic driver was probed first: it drives the captured scheduler with `OfflineAudioContext.suspend()` checkpoints. It worked in Chromium and WebKit, but Firefox 155 has no `OfflineAudioContext.suspend` (`logs/suspend-probe.log`). So the checks use the instrumented graph, which the assignment allows. The page harness:
  - wraps `createOscillator`/`createBufferSource` on the synth's context instance, and `start`/`stop` on each node it returns;
  - wraps channel 0's volume, pan and modulation AudioParams on the instance, including the `value` setter;
  - leaves `instrument.js` and every prototype alone;
  - captures the 60 ms scheduler callback when the constructor calls `setInterval`, and runs scenario steps right after a tick (for example "in the tick where play goes 1 → 0").
  
  Note times are the library's `start(when)` values, so timer jitter does not move them. Program 0 is a one-operator sine timbre, so one note is one source. Each scenario runs under a 12 s Node deadline (the longest is about 4 s of context time).
- **WebKit wrapper collection.** WebKit collected an unreferenced AudioParam JS wrapper and handed out a new one without the instance wrappers. Recording then stopped after the first tick. The harness keeps strong references to every wrapped node and param (`window.__t6tr.keep`); two WebKit runs then passed (`logs/dev-webkit-keep{1,2}.log`).
- **Seek comparison.** Effective automation follows Web Audio's timeline rules over the recorded calls: the `value` setter acts at the call's context time, `setValueAtTime` at its time, and `cancelScheduledValues(t)` removes events at or after `t`. A pass is its notes (time from the pass start, frequency, detune, waveform) plus, for each parameter, the value at the pass start and every later event. Histories must equal the fresh seek exactly. The fresh seek must equal the song's state, computed in Node from the song with the library's documented mappings (12-TET with RPN coarse tuning, bend units of 100/127 cent, GM gain `3v²/127²`, pan `(v−64)/64`, modulation `v·100/127`) and the tempo map.

### 17.6 Notes and risks

- **A regression that hangs spills into later cases.** In Firefox, a content process stuck in a loop keeps running after its page is closed, and later pages that share it hang or never start audio. In WebKit, a hung web process keeps growing (§17.5). So a reintroduced hang fails more cases than its own, in a browser that is then degraded. Pre-fix builds are no longer loaded in browsers for such cases (rule 10).
- **The seek-while-playing precondition depends on timer timing.** It needs the scheduler tick that queues tick 1200 to come less than 0.2 s after the previous tick. Measured margin: the change was due 0.168–0.174 s after the seek in every engine (`full2`). Since PR #41 round 1 (§17.9), an attempt that misses it is repeated, up to 3 times.
- **Realtime audio is required** (Firefox needs an audio output; CI starts a PulseAudio null sink). Runtime per engine: parser about 10 s, transport about 30 s, seek about 15 s.
- **The `hang` spec is unchanged** (outside the allowed files). It stays observe-only and is superseded by these assertions (§13).
- **At the T5 merge (#14).** The parser spec's URL case, like the phase-A `url` spec, detects completion through `page/xhr.js`, which waits for the XMLHttpRequest `loadend`. The T5 assignment requires a cancellable promise but does not fix the transport. If T5 moves to `fetch`, both specs should await the returned promise instead.
- **T4 merge (#11, #12, D-023, D-025), verified.** After merging `improve/integration` `7b4f5c5`, the harness assumptions still hold in the merged library:
  - one 60 ms `setInterval` in the constructor (`_tid`);
  - a realtime context from `getAudioContext()` unless `lazy` or a context is injected;
  - the instance fields `chvol`, `chpan`, `chmod`, `playTime`, `song` and `pg`;
  - `stopMIDI()` and seeks still stop voices through `_pruneNote` and `stop()`;
  - T4's `_rs` resume after a caller's stop applies `setValueAtTime` on the channel parameters, which the automation model covers.
  
  The specs pass unchanged on the merged code (§17.4).

### 17.7 Matrix runner stall at exit

**Incident.** The `full1` run (`npm run test:browser:matrix`, under the shared lock, head `5e03883`) wrote `results.json` at 17:37:08 and printed "PASS: browser matrix: chromium, firefox, webkit; 222 cases". The orchestrator process then never exited: 0% CPU for 42 minutes, holding the lock and blocking four agents. The supervisor stopped it at 18:19:31 (`sh` printed "Terminated"; the results were intact).

**Investigation.**
- The orchestrator calls `process.exit(status)` right after its last line. Nothing it loads registers an `exit` listener, and no handle can keep `process.exit()` from returning, so the process stalled in Node's own teardown (platform or threadpool shutdown).
- The process was gone before it could be inspected.
- Sixty replays of the run's ending (the `full1` results, a detached child under `run-with-deadline.js`, stringify, write, `rmSync`, print, exit; `scratch/exit-hang/tail.js`) all exited at once, as did several single-engine runs.
- No other agent's log shows the pattern. The cause was not isolated.

**Fix (`fb921cf`).** The command now only launches the orchestrator (`--orchestrator`, over IPC, stdin ignored, so workers no longer inherit the caller's stdin). The orchestrator reports its status after its last line and then exits. If it is still alive 30 s later, the launcher kills it, prints a note on stderr (§17.9: the final stdout line stays `PASS:`/`FAIL:`), and exits with the reported status. SIGINT and SIGTERM are passed on to the orchestrator, which stops the worker process groups. `--list`, the exit statuses 0, 1 and 2, `GITHUB_STEP_SUMMARY` and the CI commands are unchanged.

**Checks** (`logs/launcher-*.log`, `scratch/launcher-demo/`):
- A passing run exits 0 and a failing one (`stop-before-parse`, parser, Chromium) exits 1, both promptly. `--list` exits 0, and `--engines=,` exits 2.
- A scratch copy whose orchestrator reports and then blocks in `Atomics.wait` (0% CPU) exits 0 after 30 s, with the note.
- SIGTERM to the launcher during a Firefox transport run exits 143. The orchestrator, worker and browser processes of that run are all gone 5 s later.

**Residual.** A worker could stall the same way at its exit. It stays bounded by the 1,200 s engine deadline (`run-with-deadline.js`), not by this grace period.

### 18.4 #27 operator filters (`filters`, T12)

The row is already asserted, so no check is added.

- **An independent RBJ biquad.** `rbj()` and `mag()` in `filters.js` are the test's own cookbook implementation, in double precision:
  - low-pass `b = ((1−c)/2, 1−c, (1−c)/2)`;
  - high-pass `((1+c)/2, −(1+c), (1+c)/2)`;
  - band-pass with a constant 0 dB peak, `(α, 0, −α)`;
  - for all three, `a = (1+α, −2c, 1−α)` and `α = sin ω0 / (2·fq)`.

  The engine only sets `type`, `frequency` and `Q` on a `BiquadFilterNode`, and the browser computes the coefficients, so no engine code path is reused.
- **The browsers' conventions.** Web Audio gives low- and high-pass `Q` in dB (`α = sin ω0 / (2·10^(Q/20))`), and the engine passes `20·log10(fq)`. Band-pass `Q` is linear. The reference's linear form equals the browser's dB form exactly when the engine's conversion is right, so a wrong conversion fails. T12's mutants "linear Q for every type" and "dB Q for every type" failed 78 and 16 browser checks (T12 §7).
- **Declared bands and tolerances.** These are spec constants; their reasoning is in T12 §4.
  - `RESPONSE_DB` 0.01 dB: `getFrequencyResponse` at 256 log-spaced points from 20 Hz to 0.999 × Nyquist, wherever RBJ is above −80 dB. Measured worst: 1.1e-4 dB.
  - `PROBE_DB` 0.02 dB: the filtered-to-unfiltered amplitude of a pure tone at F, fitted over 0.2–0.45 s. Measured worst: 3.5e-5 dB.
  - `BAND_DB` 0.5 dB: the consumer fixture's octave bands from 125 Hz to 16 kHz above −60 dB, against the unfiltered render passed through the reference. Measured worst: 0.086 dB. Bands expected below −60 dB must measure at least 50 dB down.

  They stay in the spec, beside the windows and bands they belong to; `tolerances.js` holds the render spec's tolerances.
- **Reverb off.** Every response, probe, floor and fixture render uses `useReverb: 0`, and the renders use `masterVol` 0.05, below the compressor's threshold.
- **On this base.** The mutant that swaps low-pass and high-pass fails 48 of 160 checks in Chromium (§18.6).

### 18.5 Short notes on slow-attack timbres (§4.4.5): characterization and recommendation

**Mechanism** (`_note` and `_releaseNote`; upstream's code is identical):
1. An operator with attack `a > 0` starts at gain 0 (`setValueAtTime(0, t)`) and ramps to its level `v` with `linearRampToValueAtTime(v, t + a)`. The voice records one attack end, `t2 = t + a` of the timbre's **last** operator.
2. A note-off at `T` calls `cancelScheduledValues(T)` on every operator's gain. This removes every event at or after `T`. The ramp's event sits at `t + a`, so when the note lasts `D = T − t ≤ a`, the whole ramp is removed. The gain then stays at 0 from `t` to `T`.
3. At `T`, `_releaseNote` sets `v·D/(t2 − t)` when `T < t2` (or `v` when `T = t2`), and then releases with `r` (`r = 0` sets 0 at once). When `T > t2` it sets nothing, and the release starts from 0.

So for an output operator (`g` 0), the outcome depends only on its attack, its release and the last operator's attack:
- **Silent while held:** `D ≤ a` for every output operator.
- **Silent throughout:** silent while held, and either `D > a_last` or `r = 0` for each of those operators.
- **Otherwise:** if the hold was silent, a step to `v·D/a_last` sounds at the note-off and decays with `r`.

Drums are not affected, because channel 10 ignores note-offs.

**Measured** (`scripts/short-notes.js`): one C4 note per program, quality and duration, each in its own synth and `OfflineAudioContext`, with reverb off and the default level. The peak is measured while held (from note-on to 1 ms before the note-off, shifted by the compressor's 6 ms latency) and in the 0.5 s after the note-off. Silent means a peak below 2e-4, the GM audibility floor.

Coverage:
- every program with a slow-attack output (52 in quality 0, 70 in quality 1), plus controls 0, 24 and 80, at eight durations: 1,024 renders;
- all 128 programs at 0.025 and 0.07 s: 512 renders.

Results:
- The prediction matched all 1,536 Chromium renders.
- Silent renders measure exactly 0, or at most 6.1e-6 in Firefox. Sounding holds measure at least 0.070.

Programs silent with a note of duration D (identical lists for upstream):

| D | Quality 0: silent while held / throughout | Quality 1: silent while held / throughout |
| --- | --- | --- |
| 0.025 s | 24 / 1 (119) | 40 / 32 |
| 0.045 s | 17 / 1 | 28 / 23 |
| 0.07 s | 6 (91, 101, 119, 122, 123, 126) / 1 | 15 / 11: 40 Violin, 41 Viola, 42 Cello, 43 Contrabass, 44 Tremolo Strings, 101–103 FX 6–8, 119 Reverse Cymbal, 125 Helicopter, 126 Applause |
| 0.15 s | 5 / 1 | 5 / 3 (119, 125, 126) |
| 0.3 s | 4 (101, 119, 122, 123) / 1 (119) | 3 (119, 122, 125) / 2 (119, 125) |
| 0.5 s, 0.9 s | 4, 2 / 1 | 3 / 2 |
| 1.1 s | none | none |

For scale: at 120 BPM a sixteenth note lasts 0.125 s and a 32nd note 0.0625 s.

The 0.3 s row reproduces §4.4.5 (119 in both qualities, 125 in quality 1). §4.4.5 measured one window over the hold and the release, so it missed the programs that are silent only while held: 101, 122 and 123 in quality 0 and 122 in quality 1. Those sound only after the note-off, as a step of `v·D/a` decaying with `r` (peaks 0.064–0.112 at 0.3 s).

**Upstream.** `3d75aee` behaves the same:
- its `_note` envelope, `_releaseNote`, `preroll` (0.2 s) and both timbre tables are identical; the attack tables read from both are byte-identical;
- rendered with the same items, it gave the same classification in every render: 1,024 in Chromium, and 256 (0.07 and 0.3 s) in each of Firefox and WebKit;
- outside the noise programs, whose data differs by #7, peaks are equal: within 4.8e-7 relative in Chromium (its summation order, §4.3) and exactly in Firefox and WebKit;
- Firefox and WebKit classify the fork identically to Chromium.

**Realtime playback.** The sequencer sends each note-off between 0.2 s and about 0.26 s (`preroll` plus one 60 ms tick) ahead of its time. A note shorter than that is cancelled before it starts, which is the offline result above. A longer note sounds its attack until the note-off is sent; the in-progress ramp is then removed and the gain falls to 0 until `T`.

This was emulated with `OfflineAudioContext.suspend()` at `T − 0.2 s` (quantized to 128 frames: 0.3512 s for `T` = 0.55 s) and then `noteOff(T)`, in Chromium and WebKit (Firefox 155 has no `suspend`; `logs/preroll-probe-*.log`). With a 0.5 s note:
- 119 (both qualities) and 125 (quality 1) peaked at 0.078 and 0.070 before the send, then measured exactly 0 after it;
- Violin (quality 1, `a` 0.1 s) and program 0 were unaffected.

A note-off sent "now" (live input) keeps the hold, because the ramp has already sounded up to `T`.

**A related defect.** `t2` comes from the timbre's last operator, not from each operator. When an output operator's own attack is shorter than the last operator's and `D` falls between them, the release first steps that operator to `v·D/a_last`, whatever its level was. From the tables, this applies to quality 1 programs 23, 50, 86, 88 and 123 (output attacks of 0.02–0.1 s under a last-operator attack of 0.1–1 s). It is derived from the code and was not measured separately; the peaks do not isolate it.

**Decision needed** (the row stays pending):
- **A: keep upstream behavior and document it.** A note shorter than its timbre's attack is silent until note-off, and silent throughout when the release is 0 or the last operator's attack is shorter than the note. In realtime playback the attack is cut 0.2 s before the note-off.
- **B (recommended): fix `_releaseNote` with the standard technique.** For each operator whose attack has not ended at `T`:
  1. compute its own ramp value at `T`, `v·(T − t)/a`;
  2. `cancelScheduledValues(T)`, then `linearRampToValueAtTime(value, T)`, so the gain continues on its original line up to `T` (offline, with the sequencer's lookahead, and live);
  3. release from that value.

  Each operator's attack end is stored instead of the last operator's. `cancelAndHoldAtTime` would hold the value natively, but Firefox 155 does not implement it (Chromium and WebKit do; `logs/cancel-hold-probe.log`), so the re-ramp is the portable form.

  B is a sound change from upstream. It needs a ledger entry, and because the upstream differential sees different calls for notes released during their attack, a `FORK_PATCHES` entry. Its phase-B assertion would be:
  - GM 119 and 125 audible with a 0.3 s note;
  - the hold follows the ramp, and the release starts from the ramp's value;
  - the same with the lookahead emulation.

  It would also make the 11 quality-1 programs above audible for short notes.

### 18.9 PR #57 round 1: a unit-test timeout on CI, and a summary fix

On the arm64 CI runner, with the other unit files running alongside, every 44.1 kHz single-install test took about 1.25 s. - the two failing tests;
- the two-install tests, which were at half the default;
- the sample-wave test, whose literal 60 s now uses the constant.

60 s is more than ten times the worst CI time. The `vm` cost could only be avoided by changing `tests/harness.js` or how the builds are loaded, and both are outside this task.
