## 2. Design

- **One declaration.** `tests/browser/matrix.js` lists engines, builds (`source` = `webaudio-tinysynth.js`, `min` = `webaudio-tinysynth.min.js`), quality modes (0, 1), sample rates (44100, 48000), the Math.random seed, deadlines and the specs with their kind and dimensions. The runner prints it before and with the results.
- **Runner.** `scripts/browser-matrix.js` runs the analysis self-test, then one worker process per engine under `scripts/run-with-deadline.js` (1200 s, process-group kill). Inside a worker every case has its own Node-side deadline (60 s default; render 300 s, hang 6 s): at the deadline the case fails, its pages and contexts are closed from Node, and a browser that does not respond is closed and relaunched. A browser that cannot launch fails the worker and the run ("NOT LAUNCHED"); nothing is skipped. The last line is `PASS:` or `FAIL:` (the `run-regressions.js` contract). `--source=PATH`/`--min=PATH` test another copy of a build; `--out=DIR` writes `results.json` and WAV renders; `--seed=N`; `--list`. With `GITHUB_STEP_SUMMARY` set it writes a result table.
- **Kinds.** `assert` specs (embed, render, gesture, url, lifecycle) run by default and fail on any failed check. `observe` specs (hang, variation; `npm run test:browser:observe`) record baseline behavior and fail only if an observation cannot be made. Assert specs also record observations (JSON) for behavior T2–T5 will change; no failing or skipped test was committed.
- **Controlled server.** `scripts/browser-server.js` (Node `http` only) on 127.0.0.1, ephemeral port, every request logged. Routes: library builds, registered pages, `/midi/ok|status/<code>|redirect|empty|garbage|truncated/<n>|reset|hold/<key>|slow/<ms>`. `hold`/`release` make races deterministic. CLI mode serves the repository read-only for manual listening (`npm run test:browser:serve`).
- **Test pages.** Built in Node (`tests/browser/lib/pages.js`): `page/prelude.js`, optional `page/instrument.js` and the inlined library in `<head>`; page scripts in `<body>`. Render and embed pages run offline (every request aborted); gesture, URL, lifecycle and hang pages are served over `http://127.0.0.1`.
- **Seed-aware infrastructure (test only).** The prelude replaces `Math.random` with a resettable mulberry32 stream before the library loads; `render()` restarts it before construction and again before `setAudioContext()`, so generated buffers depend only on (seed, sample rate). This is not runtime policy (D-004 is T8's). The seed is printed with every run and recorded in `results.json`; `render()` reports the hashes of `convBuf`, `n0` and `n1` and the number of random values drawn.
- **Offline renders.** `page/render.js` constructs the synth, installs an `OfflineAudioContext` with `setAudioContext()`, schedules every note and controller at explicit times and renders. It stops the constructor's 60 ms interval before rendering (handle captured by the prelude; the library does not expose it, #11), because that scheduler keeps pruning voices during an offline render at wall-clock-dependent positions (§4.4). PCM is returned as base64 Float32 and analyzed in Node (`tests/browser/lib/analysis.js`), so one implementation measures every engine.
- **Analysis.** Pitch: strongest peak within ±1.5 semitones of the expectation, Blackman-Harris window, ≥8× zero padding, quadratic interpolation of the log magnitude. Self-test on synthetic tones between FFT bins with harmonics and noise: error < 0.001 cents at 44.1 and 48 kHz. Vibrato: zero-crossing instantaneous frequency. Envelope: per-period amplitude of a 300 Hz tone (an integer period at both rates), crossing times, log-linear time-constant fits.

## 4. Rendered audio

### 4.1 Scenarios and expectations

`tests/browser/lib/scenarios.js`. ### 4.3 Deterministic data versus rendered-audio tolerance

- **Deterministic data.** With the test seed, `convBuf`, `n0` and `n1` hash identically in all three engines, both builds and every run, per sample rate (44.1 and 48 kHz differ, as D-004 expects). The library draws 66,238 values at 44.1 kHz and 72,038 at 48 kHz (seed `0x5eed0001`). No tolerance applies.
- **Same engine.** Firefox renders were bit-identical everywhere (sources, builds, launches). Chromium renders with three or more simultaneously sounding inputs into one node differ between runs by up to 1.9e-7 at test levels and 5.45e-5 after the compressor at the default level: Chromium sums a node's inputs in a run-dependent order. Reproduced without the library (an `OfflineAudioContext` with three oscillators into one gain: 3 distinct hashes in 8 runs; 2 inputs: 1; Firefox and WebKit: 1; `logs/summation-order.txt`). WebKit differs only in quality-1 drum sweeps (≤ 9.3e-8): the library's percussion `onended` handlers disconnect detune inputs while the render runs. Custom-timbre scenarios were bit-identical in all engines.
- **Across engines.** At the test level the engines agree within 0.085 dB on GM energies and exactly on the makeup gain. At the default `masterVol` 0.5 Firefox's DynamicsCompressor compresses harder: GM program energy up to 3.6 dB and loud drums up to 5.5 dB lower than Chromium and WebKit, which agree within 0.01 dB (`logs/compressor-gap.txt`). That was the 2.7 % Firefox RMS gap seen in the first probe; it is DSP, not generated data.
- **Across seeds** (noise-based sounds, same engine): drum energy varies by up to 1.5 dB (Chromium, WebKit) and 2.8 dB (Firefox), the reverb tail by 4.0 dB.

### 4.4 Findings from the renders (baseline, not fixed here)

1. **The scheduler acts on offline renders.** The 60 ms interval keeps running after `setAudioContext(OfflineAudioContext)`, and the context's `currentTime` advances while it renders, so released voices are pruned (cut from about 3 % amplitude) at positions that depend on wall-clock timing. With the interval left running, three renders of one GM batch differ by up to 3e-3 (−50 dBFS); stopped, they match (variation spec). #11 (handle, dispose) and #12 (defined OfflineAudioContext behavior) should cover this; the render infrastructure stops the interval meanwhile.
2. **Unhandled rejections with an OfflineAudioContext.** `send()` calls `resume()` on the not-yet-rendering offline context and leaves the rejection unhandled: 192 per render case in every engine (2 per install plus every `send()`). Closing the realtime context the constructor created rejects its pending `resume()` (Firefox "Closed before resume completed", WebKit "AudioDestinationNode is not initialized"; 88 per case). #12/T4.
3. **Peaks beyond full scale.** In quality 1 at the default `masterVol`, drums 49 and 55 peak at 1.157 (44.1 kHz) and 1.286 (48 kHz) in Chromium and WebKit (0.69 in Firefox). Recorded, not asserted.
4. **Pitch-bend unit.** The library maps bend range units to 100/127 cent; MIDI's RPN 0 gives 100/128. ±8191 at the default range is 201.55 cents (MIDI: 199.98), and a 12-semitone range gives 1209.30 cents (1199.85). The checks assert the library's established mapping and print the MIDI value beside it. No task owns this: supervisor decision.

## 14. Risks and supervisor decisions

1. **arm64 is unexecuted.** Builds exist (§11), but launch, `--with-deps` on arm64, PulseAudio for Firefox, and WebKit's realtime audio there are first tested by the CI run. Locally WebKit could not start realtime audio with `libpulse` visible; the CI WebKit job has no PulseAudio daemon, but `--with-deps` may install `libpulse0`. If the WebKit gesture checks fail on CI with "interrupted", that is the cause to look at first.
2. **Tolerances come from x64.** arm64 uses different SIMD paths; per-engine checks against independent expectations have wide margins, but the same-engine sample tolerances (Firefox 0) may need an arm64 measurement. The CI observe step records it.
3. **Flakiness.** Realtime gesture timing (Firefox up to 1.9 s to run with a null sink) is bounded at 10 s. The Chromium same-engine tolerance (5e-4) is 9× the largest difference seen in four full runs.
4. **Decisions needed:** the pitch-bend unit (§4.4.4); whether peaks beyond full scale at the default volume (§4.4.3) matter for the consumer; whether T4's OfflineAudioContext contract should stop the realtime scheduler for offline contexts (§4.4.1).
5. **Engine facts for #7.** Seeded buffers were identical across engines here, but cross-engine PCM is not: Chromium's input summation order alone makes renders differ at the 1e-7 level from run to run.
