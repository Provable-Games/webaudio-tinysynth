## 2. Design

### T9-3: audio starts from a gesture

- Each demo builds its synth with `lazy: true`, so no AudioContext exists at load and no autoplay warning is logged (T9A §2.2 counted 5–6 per load).
- Capture-phase listeners on `window` for `pointerdown`, `keydown`, `click` and `change` call `StartAudio()`. While audio is not running, it calls `synth.resume()`, which creates the context inside the event handler and starts it. Capture runs before the page's own handlers, so a note played by the first press already has its context. Later gestures try again while audio is not running, for example after a refusal.
- An audio line (`#audio`, `role="status"`) is filled synchronously in `Init`, so the controls below it do not move (the layout check of T9 §12). Its states: "Audio is off. Click, tap or press a key to start it." (no context), "Audio is blocked by the browser. …" (a context that is `suspended` or WebKit's `interrupted`, for example one created by a Web MIDI note before any gesture), "Audio is on.", "Audio is closed. Reload the page to start it again.", and "Audio could not start (<code or name: message>). Click, tap or press a key to try again." (a `resume()` rejection, in the error colour). It is refreshed after `resume()` settles and from the page's status timer (100 ms in jstest and soundedit, 250 ms in simple), which also catches a context created outside a gesture.
- Nothing at load creates the context: soundedit no longer sends a program change at load (program 0 is every channel's default, so the editor just shows it), and jstest's `Test()` calls `resume()` before it uses `getAudioContext()`, which is `null` before the first use.

### T9-5: URL loading

- jstest's Load (ws.mid) calls `synth.loadMIDIUrl(url, {signal}).then(…, …)`: "Loading ws.mid...", then "Loaded ws.mid. Press Play." or "Could not load ws.mid (<code>). The current song is unchanged." The text shows `code`, plus `status` for `HTTP_STATUS` (`HTTP_STATUS 404`), or the `SMF_*` message (`SMF_INVALID_HEADER: no MThd header (byte 0)`); an error without a code shows `name: message`.
- The newest load wins. A second Load supersedes the first (the engine rejects it with `LOAD_SUPERSEDED`). Choosing a file aborts a pending URL load through its `AbortController`. Both rejections are ignored, so the newer load's message stands. The file loads' existing stale-read counter is shared, so a URL load also makes a pending file read stale. A URL load's other errors are always shown, because any newer song load would have superseded or cancelled it.
- **soundedit's sample song.** Installing a song is a first use (T4), so `loadMIDIUrl("ws.mid")` at load would create the context before any gesture. Starting it at the first gesture was tried and rejected: `loadMIDI()` resets every channel and silences every voice, so the response arriving just after the first press cut that note and released a latched Sustain or MIDI pedal (the existing note-release case failed 4 checks in Chromium, `logs/dev1-chromium.log`); by the same reset it would also undo a program chosen by that first change. So **Play** loads `ws.mid` when no song is loaded (neither the sample nor a file), waits for it and plays. A failure shows "Could not load ws.mid (<code>). Choose a MIDI file instead.", and choosing a file cancels the load. The visible change: the status line reads "Stopped 0 / 0" until the first Play, instead of "Stopped 0 / 15360".
- **Engine follow-up (reported, not implemented; the engine is out of scope):** a lazy synth that could parse and keep a song without creating its context (installing the graph at `playMIDI()` or the first note) would let soundedit preload again with no context before a gesture.

### T9-8: the editor on `setTimbre`

- `Edit()` builds a new operator array from the form and calls `synth.setTimbre(m, n, p)`: `m` 0 with the current program, or `m` 1 with the key on the drum channel. It never writes into `synth.program[n].p`, `synth.drummap[i].p` or the built-in tables (E6).
- Byte compatibility (T5 §4's editor decision): each operator starts as a shallow copy of the installed one, so its keys keep their order (including keys the form does not show, such as T12's filter fields), and the form's values overwrite the existing keys. An added operator starts from upstream's placeholder `{g:0,w:"sine",v:0,t:0,f:0,a:0,h:0,d:1,s:0,r:1,b:0,c:0,p:1,q:1,k:0}`, as upstream's in-place push did. `setTimbre` keeps unknown keys and their order, so `JSON.stringify(program[n].p)`, and with it the Patch text, is what upstream's in-place edit gave for the same values.
- The form's raw strings are passed, so `setTimbre` validates them: a blank field is its `TypeError` ("operator 0 v is not a number"), `g` 5 on the second operator its `RangeError` ("operator 1 g: 5 is not an earlier operator"). The editor shows "Not applied (<name: message>). The timbre is unchanged." in a `role="status"` line under the Patch field, and leaves the installed timbre as it was. A valid edit, or showing another timbre, clears it. (Upstream turned anything non-numeric into 0.)
- **Reapply after a quality change.** The editor records every timbre it installed by `m:n`. `SetQuality` calls `setQuality()`, which reinstalls the built-in timbres of that quality, then installs those again with `setTimbre`, as T5 §4 describes. Edited timbres therefore stay installed in both qualities, and unedited ones follow the quality. Upstream kept edits per quality only because they modified its built-in tables (E6). Every recorded timbre was accepted when it was installed, so installing it again cannot fail today. If it ever did, the editor drops that edit, shows the error, and installs the other edits anyway. This guard has no test, because nothing reachable from the page makes a recorded timbre invalid.
- E5: the timbre has exactly the chosen number of operators. E7: the drum shown after a quality change is `drummap[note-35]` (`DrumTimbre`). Drum range (E8): a key outside 35–81 on the drum channel installs nothing and shows "No drum sound on note N", because `setTimbre` would throw a `RangeError` there.
