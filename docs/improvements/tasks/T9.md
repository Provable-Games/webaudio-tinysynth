## 4. Design notes

- **Keyboard control state.** The vendored `<webaudio-keyboard>` ends a mouse drag only on a window `mouseup`, and ignores a QWERTY key it thinks is still down (`currentKey`). When focus is lost those events can be lost too. `ReleaseAll` dispatches a synthetic `MouseEvent("mouseup")` on `window`, which runs the control's own release path, and sets `kb.currentKey=-1`. The control library is not edited. Every widget focuses itself before registering its window listeners, so a `focusout`-triggered release never ends the drag of the widget being pressed. Without this, after a blur with the mouse down, moving the mouse over the keyboard played notes (checked: base demos fail this, §5.3).
- **Sustain.** Shift holds the pedal only while it is down (`e.key`, not the deprecated `keyCode`; repeats ignored). Focus loss releases a Shift-held pedal, as T9A §6 asks. The Sustain checkbox latches the pedal deliberately and visibly, so focus loss leaves it down: released notes keep ringing until it is unchecked. The pedal is sent to the channel it was pressed on and follows a channel change, so it is never left down on a channel the page no longer shows.
- **Cancel.** The `cancel` event (Chrome 113, Firefox 91, Safari 16.4) and an empty `change` both lead to the same message. Older engines that fire neither simply show nothing.
- **Engine fields read by the demos.** `synth.pg[ch]` (E9), `masterVol`, `reverbLev`, `loop`, `quality`; the editor still uses `program` and `drummap` (E6). The tests read `notetab`, `pg` and `sustain`. A T7 restructuring that renames these must update the demos and `demos.js`.

## 12. Follow-up after T4: Firefox "note release soundedit" failure (`t9/demos-fix`)

Base: `improve/integration` at `1500e49`. Another agent saw `npm run test:browser:demos` fail one case in Firefox. It reproduced intermittently, about half of the Firefox runs: `locator.check`/`page.check: Clicking the checkbox did not change its state` on the octave radio or the Sustain checkbox (`_evidence/t9-demos-fix/logs/repro*-firefox.log`, `diag*-firefox.log`).

**Cause: the demo and the test, not the engine.** T4 made `ready()` resolve at once (`return Promise.resolve()`; it used to poll every 100 ms). The demos now fill their selects and the test sees them ready before the first 100 ms tick of the play-status timer. Until that tick the status line is empty. When it fills, every control below it moves down one line (18–19 px). Instrumented clicks showed Playwright clicking at y=391 while the "+1" radio was at y=402–416, so the click landed on `DIV#container`. The engine behaves as T4 intends.

**Fix.** jstest and soundedit fill the status line once in `Init`, then every 100 ms as before, so nothing moves after load.

**Test that fails before the fix.** The load cases for jstest and soundedit (soundedit with the "empty" MIDI stand-in) record an element below the status line (`button[data-note='60']`, the first octave radio) once the load handlers have run, from a `setTimeout(0)` queued before them, and require it unmoved 600 ms later. Before the fix it fails deterministically in Chromium and Firefox: y 475.9 → 494.9 and 379 → 397 in Chromium, 502.9 → 521.9 and 384 → 402 in Firefox (`logs/prefix-*.log`). After the fix: three Firefox runs pass, and the three-engine run under `heavy-run.sh` passes 11/11 cases and 230/230 checks each in Chromium 153, Firefox 155 and WebKit 26.6 (`logs/final-3engines.log`). `npm run lint`, `npm test` (unit 436, node 115, regressions 3 of 3) and `npm run test:browser` pass.
