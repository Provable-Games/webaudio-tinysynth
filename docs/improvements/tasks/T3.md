## 2. Transport contract as implemented

**#8, zero-duration loops (policy: stop, not reject).** At the end of a pass with `loop` on, the scheduler wraps only if `loopEnd > 0` or the last retained event's tick is greater than the first's. Otherwise the song ends exactly as with looping off: `getPlayStatus()` becomes `{play: 0, maxTick, curTick: maxTick}`, after the one pass has played once. Another `playMIDI()` plays one more pass. `playMIDI()` itself never rejects. A `loopEnd` that is not a positive number (0, negative, `NaN`) counts as unset for this check. A positive `loopEnd` keeps a tick-0 phrase looping, with `max(loopEnd, last tick)` ticks per pass as before.

*Recorded deviation from the assignment's summary.* The assignment describes the non-advancing case as "all retained events at one tick, with `loopEnd` unset or no larger than that tick". For one tick T > 0 with 0 < `loopEnd` ≤ T, the loop does advance: the `loopEnd` wrap restores the leading rest before the first event, so each pass is T ticks long (`loop-end.js` already pins "loopEnd 4000 below the last event (6160)" as a working configuration). That loop is kept, and a test pins its period (960 ticks with `loopEnd` 480). This is not a D-005 conflict; issue #8 asks to detect a non-advancing loop, and only the loops above are non-advancing.

**#8, bounded work.** One scheduler callback handles at most 1000 events (sent messages plus tempo events). The rest are handled by the following callbacks, in order, each at its own scheduled time, so nothing is dropped or reordered. Events of a long catch-up (a throttled timer) or of a same-tick batch over about 2,000 events can therefore be sent after their time, as catch-up events always were. The bound also stops a loop that advances by nanoseconds (for example `loopEnd` 1 at 1 µs per quarter note) from blocking the page. The fixtures need at most 24 events per callback (`_evidence/t3-transport/scripts/events-per-callback.js`), so ordinary playback is unchanged: the differential and loop-end traces are identical to upstream.

**#9, silent songs (policy: stay stopped; not timed silence).** A song is silent when it has no retained event other than tempo. That covers empty files, metadata-only files (the parser keeps no meta event except tempo) and tempo-only files. `playMIDI()` on a silent song returns at once: playback does not start, no node is created (no start-up oscillator), and no state changes. The status stays as the load left it: `curTick` is the first tempo event's tick, or `maxTick` when there is no event. This holds with looping on or off and for any `loopEnd`. `stopMIDI()`, `locateMIDI()` and later `playMIDI()` calls are safe, and a normal song loaded afterwards plays to its end. A song with any other retained event (for example only a program change) is not silent. It plays as timed silence from its first to its last event, then ends. If it loops on a single tick, the #8 rule ends it after one pass.

**#10, replay.** `playMIDI()` on a completed song (`curTick ≥ maxTick`) calls `locateMIDI(0)` and then starts. The tempo returns to 120 BPM until the song's first tempo event, and the channel state returns to the seek baseline. `stopMIDI()` then `playMIDI()` before the end still resumes from the stop position with the current tempo and channel state, including manual overrides. Continuing after a seek also keeps the seek's reconstructed tempo.

**#21, seek (`locateMIDI(tick)`), per D-005.**
- No song loaded: nothing happens (no throw, no WebAudio call, no state change). It used to throw.
- Otherwise all notes stop (`stopMIDI()`), and the baseline is restored: `reset()` (program 0, bend range 2 semitones, modulation 0, volume 100, pan 64, expression 1, sustain off, bend centred, RPN null, channel tuning 0, rhythm on channel 10 only, master tuning 0), scale tuning 0 on all channels, and 120 BPM.
- Then every retained event with `t < tick` is applied in order. Tempo events set the tempo. Every other event except note-on and note-off (status `0x80` to `0x9F`) goes through the live `send()` path at the current time. That covers program change, all controllers `send()` handles (volume, pan, expression, modulation, sustain, RPN and NRPN selection, data entry for bend range and fine and coarse tuning, reset-all-controllers, the all-sound-off family), pitch bend, and the SysEx messages `send()` supports (universal master fine and coarse tuning, GS master tuning and transpose, scale tuning and rhythm part). Note: `send()` has no GM or GS reset SysEx handler; its only reset is status `0xFF`, which a parsed song cannot contain.
- Positioning is the legacy next-event rule: `playIndex` is the first event with `t ≥ tick`, and `curTick` is its tick. With no such event, `curTick` is `maxTick`. A seek to exactly the last event's tick resumes there. As before, when that event is at `maxTick` (End-of-Track at the last event), the song counts as completed and `playMIDI()` restarts from the beginning. If the song was playing, `playMIDI()` resumes it.
- Channel overrides do not survive. Engine settings do: `masterVol`, `reverbLev`, `quality`, `voices`, `loop`, `loopEnd` and custom timbres (`setTimbre`) are untouched.

**Loop wraps.** The default wrap (`loopEnd = 0`) is unchanged: no tempo reset, no channel reset, and identical traces to upstream (`loop-end.js` section 2, `differential.js`). The `loopEnd > 0` wrap keeps the fork's tempo reset and timing (`loop-end.js` section 1, four passes). Fractional tempo and detached methods are unchanged.

**Implementation notes.**
- `loadMIDI` no longer calls `reset()` itself, because `locateMIDI(0)` now does. The WebAudio calls of a load are in the same order as before (`stopMIDI`, `reset`, then a `stopMIDI` with no voices left), which the differential and parser-compat tests compare against upstream.
- The scheduler's `song.ev.length > 0` guard is gone. `playMIDI` is the only way to start playback and never starts a song without events.
- `locateMIDI` replaces the legacy controller switch (five controllers and the program) with the `send()` loop, which is why the minified build shrinks (§7).

## 8. Risks and follow-ups (for the supervisor)

1. **Stale automation on a seek during playback.** Controller automation that the scheduler already queued (up to the 0.2 s lookahead) before a seek is not cancelled, so for that window a channel parameter can still follow the old position. This is the same as legacy `stopMIDI()`. Cancelling it would add calls to every `loadMIDI` trace, which the differential test pins to upstream.
2. **`resume()` during a seek.** `send()` calls `audioContext.resume()` when the context is suspended, so a `locateMIDI(tick > 0)` before a user gesture now asks to resume. In the browser probe, `page.evaluate` gives user activation (D-011), so this could not be observed. This is for T4 (#12) to settle.
3. **Release tails on replay.** A replay right after the end cuts the last notes' release, because `locateMIDI(0)` stops all sound (D-005). Previously the tails rang into the new pass.
4. **Large same-tick batches.** A batch over about 2,000 events, or a catch-up, is spread over several callbacks, and its later events can start late. No fixture comes near this (at most 24 events per callback).
5. **Legacy positioning quirk kept.** When the next event after a seek is at `maxTick`, `playMIDI()` restarts the song instead of playing that event (D-005 "keeps the legacy result").
6. **Documentation.** The README does not yet describe the #8 and #9 policies, the seek baseline or the replay rule (T9/#20). D-005 lists "GM/GS reset" among the SysEx handled, but `send()` has none (see §2).
7. **T6.** Any phase-A browser characterization of the old transport (empty-song status, replay tempo, seek state) needs updating when T3 is integrated. `tests/browser/**` was not touched.
