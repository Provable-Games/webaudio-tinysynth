## Candidate contract

`playMIDI()` checks that the synth is live and the song has playable events, calls `prewarm()`, restores any stopped channel state, creates its existing dummy source, then reads one AudioContext-time anchor. It computes the musical opening under the existing cursor rules and immediately calls `_scheduleMIDI(anchor + preroll)`. With `loopEnd` set and the cursor at tick 0, tick 0 sounds at anchor + 0.1 s; otherwise the next event sounds at anchor + 0.1 s and tick 0 may be a virtual time before it. `preroll` is 0.5 s. The timer continues to call `_scheduleMIDI(currentTime + preroll)` at its inherited 60 ms interval. `_scheduleMIDI()` contains the prior event-walk, including the 1000-event bound and the non-advancing-loop guard. Housekeeping stays outside the extracted scheduler and runs at the existing timer/third-tick cadence.

The existing `getPlayStatus().startTime` contract is unchanged: it is the scheduler's current-pass cursor and is null when not playing. The additive, enumerable `initialStartTime` records the origin for the most recent Play run. It is stable across loop wraps and natural scheduling completion, including a non-looping song whose entire event list was consumed in the first synchronous call. Stop, successful load, seek, successful context replacement and dispose clear it. A seek during playback and a completed-song replay each start a new run with a new origin. It describes run timing, not audible-playing status.

The consumer's first visual sync must use `initialStartTime` when available and non-null, falling back to `startTime` for older pinned engines. Later visual restarts continue to follow `startTime`. The draft consumer edit is in `consumer-initial-sync.patch`; the actual checkout remains unchanged. The integration harness runs the current `player/player.js` sync closure with that patch applied in memory.

### Bounded demand probe

The resource fixture is a 50 ms repeated loop with 20 note-on/off pairs at the same tick within each pair, spread across distinct tick positions per pass, three melodic operators, one channel-9 n42 hit per pass, a 1.0 s operator release (`releaseRatio=3.5`), and `voices=64`. It is a synthetic stress input: 400 melodic note-ons per musical second exceed the configured tracked-voice budget for a multi-second tail.

At the first candidate fill the mock created 492 oscillator/buffer sources for 170 `_note()` calls (161 melodic notes and nine drum hits); it recorded 98 prunes before their `nt.e` natural ends while `notetab` stayed capped at 64. The base engine's first 60 ms / 0.2 s timer fill created 214 sources for 74 calls and recorded six such prunes. At context time 0.30 s, candidate counts were 854 sources / 294 calls / 216 early prunes versus base 492 / 170 / 98. These numbers show actual allocation and cap-pressure consequences; they do not claim that any number of voices is acoustically retained by a browser. The candidate is not made to drop or retune notes to hide this input's over-budget demand. One-note 50 ms-loop timing remains separately tested without this stress workload.

A separate tail fixture schedules note-on at 0.10 s, note-off at 0.35 s and release `r=0.03`. The first prune is at 0.54 s for both base and candidate with the existing 60 ms/third-tick cadence. This is call-timing evidence, not native captured audibility.

## Proposed decision text for D-044 (supervisor-owned; pending)

Proposed, not adopted: choose a fixed 0.5 s scheduler horizon with one immediate post-preparation fill and unchanged timer/housekeeping cadence. Preserve `startTime` as the scheduler-following pass cursor and add ordinary enumerable `initialStartTime` as the latest run's stable tick-0 origin for first visual sync. Consumers use the additive field on first sync with a legacy-field fallback, then use `startTime` for later passes. Record the material trade-off: Stop/resume remains cursor-based, so events newly submitted in the expanded 0.2-to-0.5 s window can be cancelled and skipped on resume, and controller state submitted through that cursor is restored at resume time. Natural scheduling completion does not clear the run origin; Stop/load/seek/context replacement/dispose invalidate it, and replay establishes a new one. Adoption requires the user's explicit timing decision with the measured allocator/tail evidence visible; #76, consumer migration/repin and #80 remain separate qualification gates.

## Proposed PR description

**Proposal only; timing adoption is pending the user's decision.** Protect first-play and mid-song scheduling deadlines by filling a fixed 0.5 s AudioContext-time horizon immediately after preparation and one shared clock anchor. Keep the 60 ms timer and third-tick cleanup phase. Add a stable enumerable `initialStartTime` for first visual sync while preserving scheduler-following `startTime` for later passes. The consumer migration is linked and is not shipped in this engine change.

The 0.5 s horizon intentionally expands queued-note/controller state at Stop: a 0.60 s note can be queued at 0.30 s, cancelled, and skipped when the existing cursor-based resume continues.
