## 2. Contract as implemented

### 2.1 API

**`setSampleWave(name, samples)`** registers a single-cycle table. **`setHarmonicWave(name, real, imag)`** registers a `PeriodicWave`. Both return `undefined` and act in this order, so a failure changes nothing:
1. check the name;
2. check and copy the data;
3. build the wave in the installed context, if there is one;
4. store it.

| Input | Rule (D-006 grammar, D-028 natural limits) | Error |
| --- | --- | --- |
| `name` | a string; `^n[A-Za-z_][A-Za-z0-9_]{0,30}$` for samples, `^w[A-Za-z_][A-Za-z0-9_]{0,30}$` for harmonics. A digit second (`n0`, `n1`, `w9999`, `n9`, …) is reserved for built-ins | `TypeError("wave name: <name>")` |
| `samples` | an `Array` or a typed array of at least 1 number, each in [−1, 1] (NaN and ±Infinity are outside); no upper bound | not an array: `TypeError`; otherwise `RangeError`; message `samples: an array of numbers in [-1, 1]` |
| `real`, `imag` | `Array`s or typed arrays of equal length ≥ 2 (the DC slot plus at least one harmonic), each a number that stays finite as a 32-bit float (`1e300` is rejected: Chromium and Firefox reject it in `createPeriodicWave`, WebKit accepts it); no upper bound | not an array: `TypeError`; otherwise `RangeError`; message `real, imag: equal-length arrays of >= 2 finite numbers` |

Elements must be numbers: strings, `null`, holes, booleans and BigInts are rejected rather than coerced. Array-likes, `Set`s, `ArrayBuffer`s and `DataView`s are rejected.

**Stored data.** The registry (`_wv`, a `Map`) keeps Float32 copies of the arrays, each read once (review I1), so the caller's arrays can change afterwards without effect. A harmonic wave stores `[real, imag]`, with index 0 (DC) set to 0 in both, and a sample wave stores `[samples]`.

**Extreme harmonic magnitudes (review M1).** Coefficients that are finite as floats but extreme rendered NaN: Chromium and WebKit from about 1e36, all three engines for a lone subnormal, and Firefox then kept the NaN in the graph for later, unrelated notes. When the largest magnitude is above 1e9 or below 1e-9 (and not 0), both stored arrays are therefore scaled by the power of two that brings it to about 1. The browser's normalization undoes the scale, so the wave is the one asked for. Ordinary inputs are stored and passed unchanged. The browser check renders a `3e38` set and a `1e-44` set, followed by an ordinary note, finite in all three engines. On `f00f22c` it fails in Firefox with 59,270 NaN samples (`mutation/browser/pre-M1-firefox.log`). The registry outlives contexts. There is no count limit and no memory bound (D-028); see §3 for the measured cost.

**Harmonic waves** are built with `createPeriodicWave(real, imag)` with default normalization, so the peak is 1, as for `w9999` and the oscillator types. Element `i` is harmonic `i` (cosine in `real`, sine in `imag`). Registering w9999's coefficients under a new name renders exactly as `w9999` does (browser check, max diff 0). An all-zero wave is silent in every engine; no NaN (probed, `logs/probe-engine.txt`). A million coefficients are accepted everywhere, the cost being 0.1–0.5 s to build.

**Sample waves (D-027, D-031).** For N samples at context sample rate `sr`, each sample is held for `k = max(1, round(sr / (440·N)))` frames, so one cycle takes `N·k` frames. One **guard frame**, the first sample again, follows those frames, so the buffer is `N·k + 1` frames long. Notes loop only the first `N·k` frames (`loopEnd = N·k / sr`); §4.3 explains why. The home pitch is `base = sr / (N·k)`, and `k` and `base` depend only on N and `sr`. `_mk` tags each buffer it builds with its home pitch and loop end (`_b`, `_l`). `_note` reads the tags, so a buffer is registered-or-not by what it is, not by its name (review L1, below).

N = 1 is accepted (D-028, "non-empty") and plays as a constant, DC. As an FM modulator it shifts the carrier's pitch instead of modulating it: the review measured 440 → 660 Hz for `v: 0.5` in all three engines.

| Table | 44.1 kHz: k, frames, base | 48 kHz: k, frames, base |
| --- | --- | --- |
| 8 samples (pulse) | 13, 104 (+1), 424.04 Hz | 14, 112 (+1), 428.57 Hz |
| 16 (4-bit saw) | 6, 96, 459.38 Hz | 7, 112, 428.57 Hz |
| 32 (TinyChip triangle) | 3, 96, 459.38 Hz | 3, 96, 500 Hz |
| 64 (Beast triangle) | 2, 128, 344.53 Hz | 2, 128, 375 Hz |
| 93 (short LFSR) | 1, 93, 474.19 Hz | 1, 93, 516.13 Hz |
| 256 | 1, 256, 172.27 Hz | 1, 256, 187.5 Hz |
| 32,767 (long LFSR) | 1, 32,767, 1.3459 Hz | 1, 32,767, 1.4649 Hz |

**Playing them (`_note`).** Before any voice is stolen (`_limitVoices`) or any node is created, every operator's wave is looked up in the installed context: `noiseBuf[w]` for `n*` names and `wave[w]` for `w*` names. When one is missing, the note is dropped, with no node and no stolen voice. This can only happen for a timbre written into `program`/`drummap` without going through `setTimbre`.

The note is dropped rather than throwing for a reason. The scheduler sends an event and only then advances (`send(e.m)`, `++playIndex`), so a throwing note would repeat every 60 ms forever. T5 (#13) also aims for "no note or scheduler callback ever throws". At baseline, an unknown `w*` name threw from `setPeriodicWave(undefined)` with half a voice built, and an unknown `n*` name played a silent buffer.

A registered buffer plays at `fp / base`. The pitch-envelope target is `fp / base · p`, and FM into it is scaled by `fp_target / base` on `playbackRate`, so its depth in cents matches an oscillator's (browser check: 34.2828 / −34.9756 cents on both, against 1200·log2(1 ± 0.02) = 34.2830 / −34.9756). `n0`, `n1` and buffers written straight into `noiseBuf` keep `base = 440` and loop their whole buffer, as before. That holds even when a caller writes a buffer over a registered name, as TinyChip's `registerWaves()` would on a half-migrated page. Before the review fix (L1), such a buffer took the registered name's base and played about 440 times too high. The lookups touch only `n*`/`w*` names, and no `Object.prototype` key starts with `n` or `w`; the unit tests register and play `n__proto__`, `nconstructor` and `nhasOwnProperty`.

**Replacement.** Registering an existing name replaces it transactionally: invalid data keeps the old wave, a sounding voice keeps the buffer or `PeriodicWave` it started with, and the next note gets the new one (unit and browser tests). Names have kinds by prefix: `nX` and `wX` are different waves.

### 2.2 `setTimbre` and `_checkWave` (for T5)

`setTimbre(m, n, p)` now calls `this._checkWave(p[i].w)` for every operator before anything changes; the rest of `setTimbre` is unchanged. **`_checkWave(w)` contract:**
- `undefined` is accepted (the default fills in `"sine"`).
- So are the built-ins `"sine"`, `"square"`, `"sawtooth"`, `"triangle"`, `"w9999"`, `"n0"` and `"n1"`, compared strictly with `includes`.
- So is any name registered through `setHarmonicWave`/`setSampleWave` (`_wv.has`).
- **Unsupported compatibility path** (supervisor decision, after T11's first PR draft): a string `n*` name that is an own property of `this.noiseBuf`, or a `w*` name that is an own property of `this.wave`, is accepted too. This covers a caller that wrote a buffer or `PeriodicWave` into those internals itself, as TinyChip does today. `_note` plays such a buffer exactly as before T11: on the 440 Hz basis, looping the whole buffer. It is not a public API: it depends on the installed context's internal objects, so the name is gone after `setAudioContext()` and unknown before a lazy synth's first use. `setSampleWave` is the supported way.
- Anything else throws `TypeError("unknown wave: " + w)` and has no other effect.

T5 can fold the call into its general validator unchanged. Every built-in timbre passes, since the tables use only those seven names.

The compatibility path is tested in two places:
- `tests/node/waves.test.cjs` reproduces TinyChip's `registerWaves()` and `install()` from `tinychip.js` (b16c8ef, lines 15–43): its generators, 1 s buffers written into `noiseBuf`, presets in `program[129+]`, and its drum kit installed with `setTimbre`. It then plays every preset and drum, and the WebAudio call trace equals upstream's (with the fork's tempo patch), call for call, in both builds.
- The unit test covers own properties only, the prefix match, non-strings, and the name being gone after a context change and before a lazy context.

Both tests fail on the build without the path (`mutation/unit/nocompat/`). The path costs 108 B raw and 36 B gzip in the min.js.

Behavior change (ledger L-12): an unknown name such as `"n2"`, `"w1234"`, `"custom"` or `"Sine"` now throws at `setTimbre`. Before, it threw at note-on for `w*`, played silence for `n*`, or was ignored as an invalid oscillator type and played sine.

### 2.3 Quality, contexts, lifecycle

- **`setQuality()`** keeps the registry and still resets program and drum timbres, so custom timbres must be reinstalled after it, as the consumer already does (unit and browser tests).
- **`setAudioContext()`** builds every registered wave for the new context and its sample rate first, before tearing down the old graph (review L2). If the new context refuses one, `setAudioContext()` throws and the installed graph, context and waves are left as they were (unit test). With nothing registered it makes no extra call, so the differential test against upstream still passes. A browser render of waves registered before a 44.1↔48 kHz switch matches waves registered on the new context, bit for bit.
- **`dispose()`** releases the context's waves, because T4's `_drop` sets `wave` and `noiseBuf` to `null`. The definitions are kept so that after disposal `setTimbre` with a registered name stays a "store, no effect" call (T4's post-dispose table). `setSampleWave` and `setHarmonicWave` after `dispose()` only store.
- **Lazy synths** store registrations and build them when the context is created at first use.
- **No context yet:** registration stores and builds nothing.

### 2.4 Unchanged behavior

With the registry unused, every WebAudio call is unchanged: the upstream differential, tempo and loop-end regressions pass, and so does T6's full render spec. Registering waves does not change `n0`/`n1` renders: program 119 and drums 38, 42 and 49 render bit-identically with and without 13 registered waves, in every engine.

One quirk of the engine, both before and after this change: `setBend` updates only oscillators during a note. A sample-wave voice (like `n0` before it) takes the bend at note-on and does not follow later bends. This is upstream behavior, pinned by the differential test, and the supervisor decided to keep it. **Future recommendation:** update a buffer voice's `detune` in `setBend` too, as a deliberate, ledgered change, since it alters `n0`/`n1` renders under bend.

## 3. Memory per wave and per sample rate

**Sample waves (exact):** the context buffer is `4·(N·k + 1)` bytes per context, plus the definition, `4·N` bytes, once per synth.

| Table | Buffer, 44.1 kHz | Buffer, 48 kHz | Definition |
| --- | --- | --- | --- |
| 8 | 420 B | 452 B | 32 B |
| 16 | 388 B | 452 B | 64 B |
| 32 | 388 B | 388 B | 128 B |
| 64 | 516 B | 516 B | 256 B |
| 93 | 376 B | 376 B | 372 B |
| 256 | 1,028 B | 1,028 B | 1,024 B |
| 32,767 (nNOI) | 131,072 B | 131,072 B | 131,068 B |

A short table costs about `4·sr/440` bytes, about 400 to 450 B per context. A table of `sr/440` samples or more costs about `4·N` bytes.

**Harmonic waves:** the definition is `8·(H + 1)` bytes, 520 B for 64 harmonics. The engine's band-limited tables are internal.

**Method.** `scratch/measure-memory.js` (`measure/memory.json`) measures the proportional resident memory (Pss) of the browser processes this script started. It registers M waves on a live synth, plays each once, then takes (after − before)/M; 300 waves of 64 harmonics were registered per engine and rate. The results:
- Chromium (context running): about 600 KB per harmonic wave at 44.1 and 48 kHz.
- WebKit (context suspended under the default autoplay policy): 608 KB at 44.1 kHz and 326 KB at 48 kHz.
- Firefox (suspended context, lazy tables): 21–35 KB.

The same method is too noisy for small sample waves: −297 to +24 KB for 300 waves of about 0.8 KB. For `nNOI` (expected 256 KB including the definition) it gives 393–434 KB in Chromium, 110–169 KB in WebKit, and is not usable in Firefox. Read these as orders of magnitude.

For the consumer's maximum of 16 waves, all harmonic: up to about 10 MB per context in Chromium and WebKit.

**Estimators.** Pitch uses T6's estimator (`peakFrequency`: Blackman-Harris window, 8× zero padding, quadratic interpolation) over 1 s of a note rendered alone, for both builds. Harmonic levels come from an exact-frequency DFT with the same window.

**Steps and edges.** At the home pitch, the runs of equal output frames must equal the table's runs × k exactly. Away from it, the spec measures midpoint crossings of the 12.5 % pulse, and compares the rendered pulse with an independent sample-and-hold reference whose phase is fitted to the rising edges.

**Interpolation.** Chromium and WebKit interpolate linearly, so each edge is smeared over one buffer frame, 1/k of a held step: measured 0.053–0.062 of a step for the 8-sample pulse. Firefox uses a band-limited resampler and rings around each edge: measured up to 0.124 of a step. At its home pitch Firefox also reproduces the table exactly.

**Why holding matters (D-027).** A scratch build with `k = 1`, the D-021 storage, fails the edge check at 0.775 of a step (§9), against 0.06 with holding.

### 4.2 What the tolerances do and do not promise

- Pitch is exact by construction.
- At the home pitch the output equals the table in every engine.
- Elsewhere the browser resamples, so the steps are exact in spacing (±1 frame) but their edges are interpolated: one buffer frame of linear blend in Chromium and WebKit, and band-limited ringing in Firefox.
- Rendered PCM is not byte-identical across engines.
- A short repeated LFSR is a noise texture, not NES noise clocking.

### 4.3 Chromium's loop seam, and the guard frame

While validating the home-pitch steps, Chromium 153 failed them for the 8-sample pulse: runs of 12/92 frames instead of 13/91. Probes (`logs/loop-probe.txt`, `seam-probe2.txt`, `seam-scan.txt`, `seam-rates.txt`, `seam-fixture.txt`) found the cause. For some buffer lengths, a looping `AudioBufferSourceNode` whose loop ends at the buffer end plays a wrong value for the first frame of each pass: the last frame again, or a value extrapolated beyond it.
- Affected lengths: 30 of the lengths 2–400 at 44.1 kHz (13, 26, 45, 52, 59, 90, 91, 104, 105, 118, 119, 180, …) and 29 at 48 kHz (7, 14, 28, 51, 56, 63, 95, 102, 105, 112, 119, 126, …), at every playback rate.
- Among the fixture's tables: every 8-sample table (104 and 112 frames) and `nSAW` at 48 kHz (112).
- A ramp test showed extrapolated values up to 2× full scale. For held tables, the first sample loses one frame per cycle.
- Firefox and WebKit play every length exactly.
- Setting `loopEnd` alone does not help.

**The fix** is the standard wavetable guard point: one extra frame, equal to the first sample, after the cycle, with `loopEnd = N·k/sr` (`seam-guard.txt`, `seam-guard-scan.txt`, `seam-guard-ff.txt`):
- Chromium plays every length 2–400 exactly at both rates, at rate 1 and 1.0376.
- Firefox output is bit-identical with and without it at rates 0.37, 1.04, 2.3 and 17, for six table shapes.
- WebKit differs from no guard by at most 6e-8.

The supervisor approved this as **D-031**, a refinement of D-027: buffers are `N·k + 1` frames, of which `N·k` loop. The home pitch and every D-027 property stay the same. A scratch build without the guard (`noguard`) fails the spec's pitch (−16.6 cents), steps, edges and FM checks in Chromium (§9).

**Conversion notes.**
- **Quantization.** TinyChip's shapes are float. In the consumer's i8 form they are quantized with `round(v·128)`, so `nTRI`'s ±0.6 levels become `±77/128` (0.6016). The converted wave plays exactly the quantized levels.
- **`nMET` retuning.** TinyChip built `nMET`/`nNOI` as 1 s buffers holding one table sample per frame, played at `f/440`. Their step rate was `sr·f/440` steps/s, so the noise changed with the device sample rate. Under #26 a table's `f` is its cycle frequency, giving a step rate of `f·N`, the same at every sample rate. To keep TinyChip's sound at a sample rate R, use `f_new = f_old·R/(440·N)`. The fixture retunes for R = 48 kHz:
  - drum 37: `nMET` 1760 → 2064.52 Hz;
  - drums 42 and 46: `nMET` 6160 → 7225.81 Hz;
  - drum 38: `nNOI` 264 → 0.878933 Hz.

  `tinychipOperators` keeps the originals. At 44.1 kHz the same formula gives 1896.8 Hz and 0.8076 Hz. The consumer picks one R once.
- **`nNOI` fallback (D-027) is no longer needed.** D-028 removed the 256-sample cap, and the 32,767-step LFSR registers directly at k = 1, deterministically, so it needs no `n0` and no #7. Its costs are in §6.
- **TinyChip keeps working unchanged** through the unsupported compatibility path (§2.2). Its current `install()` writes `synth.noiseBuf` and `synth.program[129+]` directly, then calls `setTimbre(1, key, …)` for its drums with `nTRI`, `nNOI`, `nMET` and `nP50`. That flow plays exactly as on upstream, call for call (node test). The recommended migration:
  1. register the waves with `setSampleWave`, as in the fixture;
  2. retune the noise drums;
  3. stop writing `noiseBuf`.

  This makes the waves survive context changes and lazy start, and gives sharp held steps at every sample rate.

## 11. Risks and notes

1. **Consumer migration (recommended, not blocking):** TinyChip's current flow keeps working through the unsupported compatibility path (§2.2, §5). The recommended move is to `setSampleWave` with retuned noise drums.
2. **The guard frame (D-031, approved):** a buffer is `N·k + 1` frames, of which `N·k` loop (§4.3).
3. **Size:** +6.6 % gzip for this step (§10).
4. **Notes are dropped, not thrown, for waves missing from the context** (§2.1). This is only reachable past `setTimbre`. It is consistent with T5's "no note throws".
5. **Mid-note pitch bend does not reach buffer voices** (upstream behavior, kept by supervisor decision, §2.4). A sample-wave lead such as TinyChip's `nTRI` takes the bend at note-on only. Future recommendation: a ledgered change to `setBend`.
6. **Firefox and high playback rates** (§7): expensive. Consumers should retune long tables rather than play them at a literal `t`. Optimization belongs to T8 (#18).
7. **Firefox demos failure (not T11):** "note release soundedit" fails in Firefox on `improve/integration` itself (§8.3), for T9-D.
8. **Very large tables:** the engine accepts them (D-028). `createBuffer` accepted 2^26 frames in every engine. A context that refuses a registered wave makes `setAudioContext()` throw before anything changes (review L2). A lazy synth's first use then fails the same way, with the synth left uninstalled. `dispose()` keeps the definitions (4 MB for a 1M-sample table) until the caller drops the synth.

## 12. Draft README/NOTICE text (CONCURRENCY.md rule 4; the supervisor adds it at integration)

**README, "What is added" bullet:**
> Custom waveforms: `setSampleWave(name, samples)` registers a single-cycle table (for example a 4-bit stepped triangle, a 12.5 % pulse or an LFSR noise table) and `setHarmonicWave(name, real, imag)` a harmonic wave; a timbre operator uses one through its `w` field. Registered waves survive `setQuality()` (custom timbres still need reinstalling) and context changes, and `setTimbre()` now rejects wave names that are neither built in nor registered.

**README, Functions entries:**
> **setSampleWave(name, samples)**
> Registers a single-cycle sample table under `name` (`n` followed by a letter or `_`, then up to 30 letters, digits or `_`; `n0`, `n1` and other names with a digit second are reserved). `samples` is an array or typed array of one or more numbers in −1..1, copied. Each sample is held for `k = max(1, round(sampleRate/(440·N)))` frames, so the wave plays near its stored rate with sharp steps, and the table's home pitch is `sampleRate/(N·k)`: an operator's frequency (`note × t + f`) is the frequency of one whole cycle, for playback, the pitch envelope and FM. Steps are exact at the home pitch; at other pitches the browser resamples, so edges are interpolated (Chromium and Safari linearly, Firefox band-limited). Long tables (for example a 32,767-step LFSR) are accepted; at a literal `t` they play at very high rates, which Firefox renders slowly, so set `t`/`f` for the cycle rate you want. Registering a name again replaces it for later notes. A one-sample table plays as a constant (DC). Throws `TypeError` for an invalid name or a non-array, `RangeError` for other invalid data.
>
> **setHarmonicWave(name, real, imag)**
> Registers a periodic wave under `name` (`w` followed by a letter or `_`, then up to 30 letters, digits or `_`; `w9999` and other names with a digit second are reserved), built with `createPeriodicWave(real, imag)`: element `i` is harmonic `i` (cosine in `real`, sine in `imag`), element 0 (DC) is ignored, and the peak is normalized to 1. `real` and `imag` are arrays or typed arrays of equal length, at least 2, of numbers that are finite as 32-bit floats; they are copied. Only the coefficients' ratios matter: very large or very small sets are rescaled before use.

**README, `setTimbre(m,n,p)` addition:**
> Every operator's `w` must be a built-in waveform (`sine`, `square`, `sawtooth`, `triangle`, `w9999`, `n0`, `n1`) or a registered name, otherwise `setTimbre` throws a `TypeError` and changes nothing. For compatibility, a name that code has written into the synth's internal `noiseBuf` or `wave` objects is still accepted and plays as before. This is unsupported: those objects are rebuilt whenever the AudioContext changes, and they do not exist before a lazy synth's first use. Register waves with `setSampleWave()` or `setHarmonicWave()` instead.

**README, Timbre Object Structure, `w` list:** add `"n…"` (a wave registered with `setSampleWave`) and `"w…"` (a wave registered with `setHarmonicWave`).

**NOTICE bullet:**
> - webaudio-tinysynth.js: added setSampleWave() and setHarmonicWave(), a registry of custom single-cycle and harmonic waveforms that timbres reference by name. Sample tables are held to a home pitch near 440 Hz and keep their own pitch basis; registered waves survive setQuality() and context changes. setTimbre() rejects unknown wave names.
