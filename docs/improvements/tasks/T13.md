## 2. Design as built

`_note` (one line): the voice's `t2` holds each operator's attack end, `p.map(x=>t+x.a)`, instead of the last operator's `t+pn.a`. Every installed timbre has `a` (`_op` fills the defaults). A raw slot a caller writes into `synth.program` without `a` gives `NaN`, which takes no branch below, as before.

`_releaseNote`, per operator `k` with attack end `e = t2[k]`, at the note-off `T`:

```js
const g=nt.g[k].gain,e=nt.t2[k];
g.cancelScheduledValues(t);
if(t<=e){
  if(e>nt.t)
    g.linearRampToValueAtTime(nt.v[k]*=(t-nt.t)/(e-nt.t),t);
  else
    g.setValueAtTime(nt.v[k],t);
  nt.t2[k]=t;
}
this._setParamTarget(g,0,t,nt.r[k]);
```

- **Attack still running (`T ≤ e`, `a > 0`).** `cancelScheduledValues(T)` removes the ramp's end event, so a ramp to the operator's own value at `T`, `v·(T − t)/a`, is put back. The gain then follows the original line up to `T`, offline, live and with the sequencer's lookahead (the line through the value already reached), and the release (`setTargetAtTime(0, T, r)`, or `setValueAtTime(0, T)` for `r = 0`) starts from it. `T = e` takes this branch too: the ramp to `v` ends exactly at `T`, and the cancellation would otherwise remove it (upstream set `v` at `T` after a silent hold). `(T − t)/(e − t)` is exactly 1 there, so the value is exactly `v`.
- **`a = 0` and `T = t`** (`e` is the note-on time): `setValueAtTime(v, T)` puts the level back, which upstream also did when the last operator had `a = 0`.
- **Attack ended (`T > e`).** Nothing is set; the release starts from the current value, as upstream did when every attack had ended. Upstream instead set every operator to `v·D/a_last` while the last operator's attack ran, which made an operator whose own attack had ended jump.
- **The cut is kept.** After the ramp, `v[k]` and `t2[k]` describe the attack as cut: a ramp to the reached value ending at `T`. `setSustain(<64)` releases every released voice on the channel again (upstream behavior). A second release at a later time then finds `T2 > t2[k]` and sets nothing, so the release keeps running. One at the same time repeats the same ramp, which the second `cancelScheduledValues(T)` removed, and one at an earlier time (callers with explicit times) lands on the same line.
- **Not used:** `cancelAndHoldAtTime`. Firefox 155 lacks it (T6 §18.5, `logs/cancel-hold-probe.log` there).

The voice keeps its fields (`t`, `e`, `o`, `g`, `q`, `v`, `r`, `f`). `_pruneNote`, stops, `dispose()` and the filters (T12, `q`) read none of `t2` and `v`. Only `_releaseNote` reads them.

## 3. Edge cases

Each has a named test in `tests/unit/short-notes.test.mjs`, run on both builds.

| Case | Behavior |
| --- | --- |
| `a = 0`, note-off after the note-on | nothing set, release from the level (as upstream) |
| `a = 0`, note-off at the note-on time | `setValueAtTime(v, T)`, then the release (as upstream when the last operator had `a = 0`) |
| `T` exactly at the attack's end | the ramp to `v` is put back; the hold is the whole attack |
| `T` at the note-on time, `a > 0` | a ramp to 0 at `T`: silent, no `NaN` |
| note-off before its own note-on | `noteOff` skips the voice (`t >= nt.t`), so nothing is released, as upstream |
| `r = 0` | the ramp, then `setValueAtTime(0, T)` |
| sustain pedal | a note-off under the pedal releases nothing; the pedal-up releases at its own time, with the ramp to the value there if the attack still runs, and with nothing set if it has ended |
| second release (pedal-up after a note-off) | later: nothing set, the first release keeps running; same time: the same ramp again |
| drums | a note-off on a rhythm channel does nothing (`noteOff` returns first) |
| `allSoundOff`, `stopMIDI` during the attack | the voice is pruned as before (`cancel(0)`, value 0), no ramp |
| a note T5.2's guard skips | no voice, so its note-off makes no call |
| a filtered output operator (#27) | its gain is released the same way; the filter gets no automation |
| two output operators, the last with the longer attack | each releases from its own value; the one whose attack ended is not stepped to `v·D/a_last` |

The quality-1 programs whose output operator's attack is shorter than the last operator's (23, 50, 86, 88, 123) and the programs silent with a 0.07 s note (quality 0: 91, 101, 119, 122, 123, 126; quality 1: 40–44, 101–103, 119, 122, 125, 126) have their own tests, with expected values taken from the note-on's own ramp.

**The invariant.** For every built-in program in both quality modes, at durations 0, 0.025, 0.045, 0.07, 0.15, 0.3, 0.5 and 1.2 s and at each operator's exact attack end, the tests evaluate each operator gain's automation with Web Audio's AudioParam rules (a small evaluator in the test, over the mock's recorded calls). The automation must equal the note-on's envelope before `T`, start the release from that envelope's value at `T`, and end with the operator's own release. The pre-fix build fails it (silence before `T`), and so does the last-operator mutant (a step at `T`).

## 5. A sound change beyond short notes: the install's warm-up note

Each install sends a velocity-1 note-on and its note-off at the same time (upstream code, unchanged). In quality 1, program 0 has an output operator with `a = 0` and an FM operator with `a = 0.01`. Upstream set the output operator to `v·0/0.01 = 0` (the last operator's attack). The fix releases it from its own level, as quality 0 (one operator with `a = 0`) always did.

**Reading taken:** the `a = 0` operator's attack has ended at `T = t`, so "completed attacks keep today's behaviour" could be read as keeping it silenced. Defect 2 of #59 says each operator releases from its own value, and the user chose to fix both, so that reading was followed. The supervisor can choose otherwise. Keeping the old result would need a special case for zero-length notes.

Measured (`scripts/blip-probe.js`, `results/blip-<engine>.json`): an install on an OfflineAudioContext with no notes, default `masterVol`, 2 s.

| Engine | Build | q0, reverb off / on: peak | q1, reverb off / on: peak | q1 after 1 s, off / on |
| --- | --- | --- | --- | --- |
| Chromium, WebKit | base and fixed | 0 / 0 | 0 / 0 | 0 / 0 |
| Firefox | base | 6.5e-6 / 7.0e-6 | 0 / 0 | 0 / 0 |
| Firefox | fixed | 6.5e-6 / 7.0e-6 | 8.2e-6 / 7.8e-6 (−102 dBFS) | 1.2e-9 / 2.4e-9 |

Chromium and WebKit render a zero-length note, `setValueAtTime(v, t)` with the release starting at the same `t`, as silence on both builds. So the change is audible in no engine and measurable only in Firefox. There it moves two `render` readings in quality 1 off zero, both within their tolerances. Firefox renders are bit-identical, so these values are stable:
- idle output after 1 s: 1.17e-9 (reverb off) and 1.38e-9 (reverb on) against 1e-8;
- the drum-length tail: 3.1e-10 of the note level against 1e-9.

The `render` spec passed in Chromium and Firefox on the fixed build (`logs/gate-render-<engine>.log`).

## 6. Browser spec (`short-notes`)

`tests/browser/specs/short-notes.js`, one `matrix.js` entry, dims `build`. Every note is rendered alone, in its own synth on an injected OfflineAudioContext, with reverb off. All its renders end on their own, so the pre-fix build may run there (rule 10).

| Case | What is asserted |
| --- | --- |
| `held` | Every program in both qualities at 0.025, 0.07 and 0.3 s. The hold peak (note-on to 1 ms before the note-off, shifted by the compressor's 6 ms) is at least `audiblePeak`. Before output time `T`, the render equals the same note without a note-off, within `FOLLOW` of the peak |
| `release level` | Two operators at fixed 400 Hz (a 0.02 s) and 1000 Hz (a 0.5 s, the last), note-off 0.1 s after the note-on, `masterVol` 0.05. The DFT-bin amplitudes over 20 ms before the note-off equal the uncut note's. After it, the ratio to the uncut note in the same window equals the operator's own value at `T` decaying with `r` = 1 s, within `LEVEL` |
| `preroll` | `OfflineAudioContext.suspend()` at `T − 0.2 s` (quantized to 128 frames), then `noteOff(T)`. Programs 119, 125 and 40 (q1) and 119 and 40 (q0), 0.5 s notes, sound until `T` and render as the pre-scheduled note-off. In Firefox, which has no `suspend()` here, the check records that and asserts that only Firefox lacks it |
| `completed` | Every program with an attack, both qualities, released 0.1 s after its longest attack, renders as with upstream 3d75aee's `_releaseNote`. That release is swapped onto the synth after its install, so both renders carry the same warm-up. The comparison uses `sameEngineSample`, with at most two re-renders, each recorded (render.js's reconciliation) |

**Tolerances** (spec constants, measured in the development runs, `results/dev2-*`, `dev3-firefox`):

| Constant | Value | Measured max |
| --- | --- | --- |
| `FOLLOW` | 2e-4 of the peak | Firefox 6.0e-5 (q1 84, 0.07 s), WebKit 1.7e-5, Chromium 1.3e-5 (q1 96, 0.3 s) |
| `LEVEL` | 5e-3 relative | 1.9e-3 in every engine (the same value: the measurement's own approximation) |
| `PREROLL` | 1e-4 of the peak | 0 (bit-identical) in Chromium and WebKit |
| `completed` | `sameEngineSample` | Chromium 2.75e-6 (5e-4 allowed), Firefox 0, WebKit 0 |

**Engine facts found on the way** (each reproduced by a probe in `scratch/`):
1. **The compressor reads ahead.** At the default level the DynamicsCompressor's detector sees its input 6 ms before the delayed output, so its gain reacts to a note-off from output time `T` on. A note whose attacks have all ended differed from its uncut render by up to 1.6e-3 of the peak in `[T, T + 6 ms)`. The follow window therefore ends 1 ms before output time `T`, while the hold-peak window still runs to `T + 6 ms − 1 ms`.
2. **Firefox puts automation times on whole frames.** Re-ending a ramp at a time that is not a whole frame (0.075 s = 3307.5 frames) changes its slope by half a frame over the ramp: 4.5e-4 = 0.5/1102.5 of the level at 0.025 s. This was measured with plain Web Audio nodes as well (`scratch/follow-debug.js`); Chromium is bit-identical. The spec's note lengths are whole frames at 44.1 kHz.
3. **The output gain settles at context start.** A held note's amplitude rises by 7 % between 0.15 and 0.25 s after an OfflineAudioContext starts, at every `masterVol` (exactly linear, so not compression; `scratch/level-debug.js`). The release-level case starts at 0.4 s and compares short and uncut notes in the same window.
4. **No offline `suspend()` in Firefox 155**, so Firefox's realtime lookahead is not emulated. The offline cases cover its release automation, which is the same calls.

### 8.1 The failing check: T12's consumer fixture in Firefox

The `filters` spec's consumer-fixture check failed: drum 42 (the high-passed hi-hat) in its 250 Hz band, 0.925 dB at 44.1 kHz and 0.526 dB at 48 kHz, against `BAND_DB` 0.5 dB. It passes on the base. The cause is §5's warm-up note.
- It is unfiltered program-0 output at 261.6 Hz.
- In Firefox quality 1 it now decays from 8.2e-6 at time 0, and the fixture's hi-hat starts at 0.05 s.
- The fixture check assumes the fixture is the only source. In the hi-hat's lowest bands, which the 3 kHz high-pass empties to −43.6 dB, the tail counts as fixture output.

**Probe.** The fixed build with only the install's two warm-up `send()` calls removed (`vacuity/no-warmup`, Firefox) passes the fixture check, worst 0.234 dB. That probe fails one unrelated check, "fq at its floor … a later note on another channel sounds unchanged" (1.089×), whose reference render depends on the warm-up. Removing the warm-up is not a candidate.

So no rule can keep both qualities' zero-length notes as upstream had them while removing the last-operator dependence (defect 2). Upstream gave `v` for every operator when the last operator has `a = 0` (quality 0) and `0` otherwise (quality 1). Whatever T13 does at D = 0 changes one quality's warm-up. §11 asks for the decision.

## 11. Decision needed: zero-length notes (blocks the PR)

The branch is not pushed and the PR is not opened, because the full matrix fails §8.1's check. Both candidates were measured. Each is a ready diff in `_evidence/t13-short-notes/scratch/`.

**C1: keep the own-level rule (the code as committed), and start T12's fixture after the warm-up tail.** Diff `C1-filters-fixture-start.diff` (`tests/browser/specs/filters.js` only): a constant `FIX_START = 1` s shifts the fixture's notes and windows. Measured with the fixed build, `filters` passes 8/8 in every engine. The worst fixture bands are:

| Engine | 44.1 kHz | 48 kHz |
| --- | --- | --- |
| Firefox | 0.004 dB | 0.034 dB |
| Chromium | 0.009 dB | 0.086 dB (T12's documented worst) |
| WebKit | 0.007 dB | 0.012 dB |

- The statement the unit invariant makes stays universal: every program, every duration including 0.
- The cost is another task's spec: the fixture's timing changes.
- The Firefox-only warm-up of §5 stays: −102 dBFS in quality 1, inaudible.

**C2: a zero-length note is silent.** Diff `C2-zero-length-silent.diff`: the `a = 0`, `T = t` branch sets 0 instead of `v`. The warm-up is then exactly silent in every engine and quality. Firefox's quality-0 warm-up, 6.5e-6 on the base and upstream, also becomes silent: a change from upstream at quality 0.
- Measured in Firefox: `short-notes` 24/24, `filters` 160/160 (worst 0.070 and 0.121 dB, drum 42 at 125 Hz), and `render` 500/500, with quality 1's idle and drum-tail readings back to 0.
- Its cost is 6 of the 52 unit tests (`vacuity/zero-silent/unit.log`): the invariant at D = 0 (an `a = 0` operator's envelope is `v` at `t`, so a release from 0 is a step) in both qualities, and the "`a = 0` at the note-on time sets the level again" test. Both would need a written zero-length exemption.
- The second `FORK_PATCHES` entry's text would change the same way, and the README bullet would say that zero-length notes are silent.

**Recommendation: C1.** It keeps one rule, each operator released from its own value, with no special case. Its only collateral is a test's assumption, broken by a −102 dBFS Firefox tail that no engine makes audible. C2 makes the install exactly silent everywhere, at the price of a special case and a quality-0 change from upstream.
