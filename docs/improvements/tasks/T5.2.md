## 2. Item 1: AudioParam values (F5, D-030)

AudioParam values are WebIDL `float`: a value that is not finite, or that rounds past the largest float32 (from 2^128 − 2^103 ≈ 3.4028235677973366e38), throws a `TypeError`. A negative time throws a `RangeError`. `setTargetAtTime`'s time constant is a `float` in the specification. The browser case records what each engine does with these calls on its own (§7):

| Call | Chromium 153 | Firefox 155 | WebKit 26.6 |
| --- | --- | --- | --- |
| `frequency.value = 1e39` | TypeError | TypeError | TypeError |
| `setValueAtTime(NaN, 0)` | TypeError | TypeError | TypeError |
| `setValueAtTime(0, -1)`, `start(-1)` | RangeError | RangeError | RangeError |
| `setTargetAtTime(0, 0, 1e39)` | **accepted** | RangeError | TypeError |

So the time constants `d`, `r` and `q` break Firefox and WebKit but not Chromium, as F5 said, and every engine rejects a computed value past float32.

**At `setTimbre` (`_op`).** The times `a`, `h`, `d`, `r` and `q` must be ≥ 0 and finite as float32 (`f32(x)`, which is `isFinite(Math.fround(x))`). Otherwise the call throws `RangeError("operator 1 d out of range: 1e+39")`, the §4 style, before anything changes; numeric strings are coerced first, so `"1e39"` is caught too. `d`, `r` and `q` reach `setTargetAtTime` unchanged as time constants. `a` and `h` are only ever added to a note time (`t+a`, `t+a+h`); bounding them keeps those sums finite for every finite `t`, so no note-time check on times is needed. `d` also feeds a drum's `stop(t + 3.5·d)`, which stays finite. The bound is the float32 range itself: the largest float32 and the largest double that rounds to it are accepted, and the next double is rejected (unit test). `t`, `f`, `v`, `s`, `p` and `k` stay "finite": they are factors, and what they compute is checked per note. A `k` of 1e39 is exact at note 60, for example, where key tracking is 2^0.

**At note time (`_note`): the note is dropped before anything is made.** T11's first pass over the operators already resolves every wave and drops a note whose wave is missing, before `_limitVoices` steals a voice or any node is created. That pass now also computes, for each operator `i`, every AudioParam value its voice writes:

- the pitch `fp[i]/b[i]` (an oscillator's `b[i]` is now 1, so this is its frequency, and a buffer's playback rate at its home pitch);
- the pitch-envelope target `fp[i]/b[i]·p`;
- the level `vp[i]`: into the channel (velocity² / 16384 · v), FM into operator `j`'s pitch (operator `j`'s `fp/b` · v), or AM into its gain (v), times the key tracking 2^((n−60)/12·k);
- the sustain level `s·vp[i]`.

If one of them is not finite as float32, the note is dropped there. The second pass keeps every write as it was and uses the values computed in the first.

Why drop the whole note rather than clamp or skip an operator:
- **No partial voice and nothing stolen.** The check runs before `_limitVoices`, so no node is created and connected and no sounding voice is stolen for a note that cannot play. Nothing needs tearing down. This is the same pattern and the same place as T11's missing-wave drop.
- **Clamping is not defined for every case.** `0 · 2^1000` is NaN (a silent operator with a huge `k`). An overflowing FM depth clamped to 3.4e38 Hz is noise, not the timbre. A clamp would also need code at each write.
- **Skipping one operator** leaves the operators that modulate it with no target, and changes the timbre into a different one at some notes only.

A dropped note is silent, the same at every call, and changes nothing. Underflow is not overflow: `k` 30 at note 0 gives a level of 2^−150 · 0.3, which rounds to 0 as float32 and plays (unit test).

**Values not checked, because they are bounded:**
- `_filter`: the cutoff is `min(…, 0.45·sampleRate)`, and `Q` comes from `fq ≥ 2^−126` (T12).
- `_releaseNote`: `v·(t−t0)/(t2−t0)` with the fraction in [0, 1].
- Detune: bend ≤ 12,900 cents, with modulation ≤ 100 cents from the channel LFO.
- The channel state: tunings from RPN and SysEx are bounded (the GS master tuning reaches about +554 semitones with out-of-range nibbles), so the note frequency `f` is between about 0.004 Hz and 1.5e21 Hz, finite as float32. It reaches AudioParams only through the checked values and the clamped filter cutoff.

Bend reaches the voice only through detune, so "depends on bend" reduces to these bounds. Tuning and note enter through `f` and are covered by the check (unit tests: master coarse tuning +63 by SysEx drops a note that fits without it, and a note that fits at 60 overflows at 127).

**Bit-exactness.** Hoisting does not change any written double: `x/1` and `x·1` are exact, and the operand order is kept. When `k` is 0, the key tracking is `2^(±0) = 1`, which upstream skipped. The differential regression (upstream plus the tempo patch, every MIDI fixture, exact `_note` and WebAudio traces) passes, and so do T11's and T12's unit and browser tests.

**Before the fix** (the browser case on the base build, §7): every overflow case threw from the middle of `_note` in all three engines, after creating 1–21 nodes, and `setTimbre` accepted time fields of 1e39. In Firefox the base build's render held **non-finite samples**; with the fix every render is finite.

## 3. Item 2: `tsmode` (F7)

`_tsConv(t)`: for `t > 0` with `tsmode` set, the converted time `t·0.001 − tsdiff` is clamped at `currentTime` (`Math.max`). A `performance.now()` time from before the context was created converts to a negative time, which every engine rejects. A time that is merely past now plays now, instead of being scheduled in the past, where the envelope would start part-way through. Times without `tsmode`, and 0 or omitted, are unchanged (a past context time still passes through as before; unit test). Without a context (a lazy synth before first use, or after `dispose()`; `noteOff` reaches `_tsConv` without `_live()`), "now" is 0, as before, and nothing throws (unit test; the mutant without that guard is killed). Before the fix, all three engines threw a `RangeError` (negative time) from `noteOn` (§7).

## 4. Item 3: the Codex LOWs (T5.md §25)

- **`loadMIDIUrl`** reads `opts.signal` as the first step of the promise executor. A throwing getter, or an `opts` proxy that throws on any read, makes the returned promise reject with the getter's own error, instead of the call throwing. No request is sent and no pending load is superseded, because both happen after the read. The README's "It never throws" now holds for hostile `opts` too. An ignored rejection is still handled (node test, under real Node promises).
- **`send()`**: a SysEx status needs at least one byte (`n = L || 1`), so `{0: 0xF0, length: 0}` is a malformed no-op decided before `_live()`: no WebAudio call and no lazy context. Negative or fractional lengths were already no-ops. `[0xF0]` and `{0: 0xF0, length: 1}` stay well formed, as before (unit test).

## 5. Item 4: wait for the previous `close()` on a lazy restart? Recommendation: no

The scenario is a lazy synth whose first use fails to install, because a registered wave is refused by the new context. Since #47, `_create()` closes that context and rethrows. A caller who retries synchronously gets a new context at once, while the previous one's `close()` is still pending, so contexts can briefly accumulate until their closes resolve (Codex P2 on #47).

Recommendation: **keep D-035's decision and do not gate.** loothero's three reasons on #47 still hold:
1. **The trigger.** It needs a context that refuses a wave that has already been validated, and no engine did that in T11's probes. Refusal is deterministic, so a synchronous retry fails the same way and the caller sees each error.
2. **The cost.** A new lifecycle state, "closing", in which the guarded methods must either throw a new error or silently do nothing. Either is a change to the D-018 lazy-start contract.
3. **What #47 fixed.** The real leak is gone: every failed context is closed.

T5.2 adds a fourth point, a **risk** to the case that `lazy` exists for. For `resume()` to wait, it has to create and resume the context after an `await`, that is, after the click or key handler has returned. Whether that still counts as the user's gesture depends on the engine's transient-activation window (WebKit is the strictest), and a close usually settles within milliseconds. T5.2 did not measure this. If the window is missed, the retried context stays suspended on exactly the tap-to-start path (D-018, T4 #12). The decisive cost remains reason 2.

T5.2 also makes the trigger rarer: `_note` can no longer throw for valid input, so a failed install is the only failure left on that path.

Measured cost of a minimal version: a prototype in a scratch copy (`scratch/item4-variants.json`) keeps the pending close, makes `_create()` return nothing while it is pending (so the guarded methods silently do nothing), and makes `resume()` wait for it. It adds +170 B raw and +41 B gzip, plus its tests. It is not committed.

The cheaper mitigation is documentation. Retry a failed first use from a later user gesture, as `resume()`'s rejection naturally invites, not in a synchronous loop. By then the earlier `close()` has resolved.

## 10. Decisions and open points

- Dropping a note whose values overflow is silent. No `debug` log was added: the consumer measures gzip size, and a debug branch would cost bytes on the hot path.
- `fk`-tracked filter cutoffs below 2^−126 are subnormal but finite (`f·ff` with a very low note and negative tuning). That is T12's behaviour and was not changed; it never throws.
- Item 4 is a recommendation only (§5).
