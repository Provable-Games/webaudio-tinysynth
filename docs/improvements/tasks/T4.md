## 2. Contract as implemented (D-018)

**Default construction is unchanged.** `new WebAudioTinySynth()` and the legacy options create the internal context at once, build the same graph, play the warm-up note and start the 60 ms interval; `isReady` is 1 and `ready()` works as before. The differential test confirms construction, loading and playback make exactly upstream's WebAudio calls (with only the fork's tempo patch applied to the reference).

**Constructor options**, checked before anything is created (no context, node, timer or table change on failure):

| Option | Accepts | Rejects with `TypeError` |
| --- | --- | --- |
| `context` | an `AudioContext` or `OfflineAudioContext` (duck-typed: `createGain()` and `destination`, so cross-realm and prefixed contexts pass); `null`/`undefined` mean "none" | anything else, including an `AudioNode` |
| `destination` | with `context`: an object with `connect()` whose `context`, if present, is that context; default `context.destination` | given without `context`; not a node; a node of another context |
| `lazy` | `true` or `false` | any other value, or `true` together with `context` |

The `TypeError` message names the option: `"lazy"`, `"context"` (also for a `destination` without a context) or `"destination"`.

**Ownership.** A context passed through `context` or `setAudioContext()` is caller-owned and never closed. A context the synth creates (eagerly, lazily or from `resume()`) is synth-owned. Passing the installed context back to `setAudioContext()` rebuilds the graph and keeps its ownership.

**Lazy start.** With `lazy: true` the constructor creates no context and no node (the interval is created, as for every instance, and does nothing without a context). The context is created by `resume()` or by the first call to a method that makes sound or sets channel or song state: `send`, `noteOn`, `setProgram`, `setBendRange`, `setBend`, `setSustain`, `setModulation`, `setChVol`, `setPan`, `setExpression`, `loadMIDI`, `locateMIDI` and `playMIDI`, and so also `reset()`, which calls the channel setters (review F5). Creating it before any channel state is set matters: installing a graph runs `reset()`, so a program change made before the context existed would otherwise be lost (tested: `send([0xc0,40])` then `noteOn` plays program 40). Settings (`setQuality`, `setTimbre`, `setMasterVol`, `setReverbLev`, `setVoices`, `setLoop`, `setLoopEnd`, `setTsMode`), getters, `stopMIDI`, `noteOff`, `allSoundOff` and `resetAllControllers` do not create it; `getAudioContext()` returns `null` until it exists. `loadMIDI` counts as a first use, so a page that loads its song before the tap creates the context then; it starts blocked, and `resume()` from the tap starts it. The README tells lazy pages to call `loadMIDI()` and `reset()` in the click handler or after `resume()` (review F5, F6: documented, not changed).

**Guard mechanism.** Each of those 13 methods starts with `if(!this._live()) return;`: `_live()` creates the lazy context if needed and is false after `dispose()`. The methods are the instance's own arrow functions, so a detached reference (`const {noteOn} = synth`) is guarded too, and they keep their names and declared arity (review F4; `2fe1882` had instance wrappers that reported `length` 0 and an empty name).

**`resume()`** returns a promise:
- after `dispose()`: rejects with an `Error` whose `code` and `message` are `SYNTH_DISPOSED`;
- creates the lazy context first, synchronously, so it is created inside the gesture;
- a closed context: rejects with `AUDIO_CONTEXT_CLOSED` (as `code` and `message`) without calling `context.resume()`;
- an `OfflineAudioContext`, or a running context: resolves at once without action;
- otherwise (`suspended`, or WebKit's non-standard `interrupted`): calls `context.resume()` synchronously within the call and settles with it, rejecting with the context's own error. Each call asks the context (no coalescing).

**`send()`'s internal resume (T3 review F9).** It asks a `suspended` or `interrupted` context at most once per context and task (the flag holds the context, so a context installed in the same task is still asked: review F2): a seek replaying many events through `send()` calls `context.resume()` once, and a later task may ask again. Re-asking on later tasks is required: in Chromium a `resume()` made without user activation stays pending, and the README path (click, then `playMIDI()` only) starts because a later `send()` asks again after the click (T6 §5; asserted by the start spec). Every internal `resume()` promise has a rejection handler, and an offline or closed context is never asked.

**`dispose()`** returns a promise, the same one on every call, and never rejects. In order:
1. marks the instance disposed (every guarded method becomes a no-op);
2. clears the scheduler interval and stops MIDI playback;
3. runs the pending-work cancellers once each (a failing one does not stop the disposal). `this._pend` (a `Set` of functions) is the hook for T5: a URL load adds a function that aborts its request and settles its promise, and removes it when the load ends. (`ready()` resolves at once and needs none since `c8b3354`.);
4. releases the song;
5. tears down the graph (`_drop`): every melodic voice, voice stopped but not yet ended (`_gone`), percussion hit, start-up oscillator and the LFO is stopped (`stop()` in a `try`, since some engines throw on a second stop) and its `onended` callback replaced; then every graph node (`out`, compressor, convolver, reverb gain, the channel volume, modulation and pan nodes, including nodes a caller swapped into `chvol`) is disconnected, which also removes every modulation route to a voice's `detune`; all references are released. A source and its gain are disconnected at once when the context closes now, is already closed (review F3) or is offline, and from its `ended` event on a realtime context that stays open (§5). The caller's destination node is never touched;
6. closes the context only if the synth created it and it is not closed yet, and resolves after that close settles (a failed close still resolves).

**Post-dispose behavior, per method:**

| Method | After `dispose()` |
| --- | --- |
| `send`, `noteOn`, `setProgram`, `setBendRange`, `setBend`, `setSustain`, `setModulation`, `setChVol`, `setPan`, `setExpression`, `loadMIDI`, `locateMIDI`, `playMIDI` | do nothing, return `undefined` (guarded; `loadMIDI` does not parse) |
| `noteOff`, `allSoundOff`, `resetAllControllers`, `stopMIDI`, `reset` | nothing audible: no voice or node is left; they only update the instance's channel fields |
| `setMasterVol`, `setReverbLev`, `setQuality`, `setTimbre`, `setLoop`, `setLoopEnd`, `setVoices`, `setTsMode` | store the value; no audio effect |
| `getPlayStatus()` | `{play: 0, maxTick, curTick}` (polling callers keep working) |
| `getAudioContext()` | `null` |
| `getTimbreName()` | the name, as before |
| `setAudioContext()` | does nothing (no validation, no adoption) |
| `init()` | does nothing: it runs once, in the constructor (also before `dispose()`: review F9) |
| `loadMIDIUrl()`, `loadMIDIfromSrc()` | still send the request (unchanged until T5); the response's `loadMIDI` is a no-op (browser-tested with a held response) |
| `ready()` | resolves (at once, as always since `c8b3354`) |
| `resume()` | rejects, code `SYNTH_DISPOSED` |
| `dispose()` | returns the same promise |

No library timer exists after `dispose()`. A percussion hit that ended before the disposal keeps its own `onended`, which only disconnects its own nodes and a guarded `chmod` route and cannot throw (tested by calling it after `dispose()`).

**`setAudioContext(ctx, dest)`** validates exactly as the constructor (a `TypeError` changes nothing), returns at once after `dispose()`, then tears down the previous graph as in step 5 and closes the previous context only if the synth created it (and it is not the new one). The new context is caller-owned. On an `OfflineAudioContext`, MIDI playback stops (`play` 0) because `playMIDI` needs a realtime context. Song, playback position and settings are kept, as before.

**Voice cleanup during play.** Upstream left stopped voices connected (T6 §7: 69 live edges against 59). Now a pruned voice (`_pruneNote`) and an ended percussion hit disconnect their sources and gains from their `ended` handler; a pruned voice stays in `_gone` until all its sources have ended (PR #37 Codex LOW; `2fe1882` dropped it at the first one), so a teardown still reaches it. Percussion hits and `playMIDI`'s silent start-up oscillator (which connects straight to `context.destination`) are tracked in `_src` until their stop time passes (the timer drops them); the start-up oscillator disconnects itself when it ends.

## 3. `stopMIDI()` (D-023, scheduled percussion D-019)

D-023 added this to T4 within #11, so the consumer can drop its `stopMIDI()` workaround (swapping `chvol` nodes and cancelling `chmod`/`chpan` automation).

- **A caller's `stopMIDI()`** silences everything the transport scheduled: melodic voices (as upstream); every percussion hit, sounding or already scheduled in the 0.2 s lookahead (hits that have already ended are just dropped); and the channel volume, pan and modulation automation queued for later, cancelled with `cancelScheduledValues(currentTime)` on all 16 channels. That includes changes a caller scheduled with a timed `send()` or setter, which is new public behavior.
- **Resume after a stop (review F1).** The scheduler sends song events up to 0.2 s ahead. A caller's `stopMIDI()` moves the transport back over the events it had sent that are not due yet, so the next `playMIDI()` sends them again: the controller changes the cancel removed are re-applied in song order, and notes cut inside the lookahead are replayed (upstream lost them). `curTick` after a stop moves back by at most 0.2 s of ticks. Without this (`2fe1882`) a stop then play kept the reset level and centre pan when a CC7/CC10 change was in the lookahead: 16x louder and centred in all three engines and both builds (review S5; the new browser check reproduces 16.3x on `2fe1882`). Residuals: the rewind does not cross a tempo event, nor a loop wrap; events sent ahead before either keep their cancelled automation (rare: both must fall in the 0.2 s before the stop).
- **Caller-timed changes (PR #37 Codex MEDIUM at :763).** A volume or expression change a caller scheduled for later (`send(msg, t)`, timed setters) is cancelled, but its value stays in the channel's stored volume or expression, so a later untimed CC7/CC11 is computed from it. This is upstream behavior (the setters store their value when called, even for a later time): the base build gives the same result for the Codex sequence (review `probe-codex.txt`: gain 0 in both). Not changed; documented in the README `stopMIDI()` entry.
- **A seek** (`locateMIDI(tick)`) stops the same way; T3's own cancel loop moved into `stopMIDI()`, with the same calls.
- **`loadMIDI`'s internal stops** (its own and the one in `locateMIDI(0, load)`) use the private `_halt()`, the upstream stop, so a load keeps upstream's WebAudio calls; `parser-compat`'s "replacing a playing song makes the same WebAudio calls" pins it against pure upstream.
- **`allSoundOff()` and CC 120/123–127** keep their upstream behavior (melodic voices only). `reset()` too.
- `stopMIDI()` takes no argument (`length` 0), so `button.onclick = synth.stopMIDI` (an `Event` argument) is a full stop (tested). An earlier commit (`db5f730`) used a `stopMIDI(load)` flag, which an event listener would have triggered; `f3aa2fd` replaced it with `_halt()`.
- **Compatibility note, not a supported API:** a node a caller swapped into `chvol[ch]` gets the cancel, and `dispose()` disconnects it (tested).
- Replaying a completed song keeps the previous pass's hits, like its melodic voices (D-019): `playMIDI` hides `_src` from the replay's internal `locateMIDI(0)` as it hides `notetab`. `dispose()` and replacement stop every hit.

Browser evidence (dispose spec): ws.mid plays into an injected `AnalyserNode` destination with two drum hits and a channel volume change queued ahead; after `stopMIDI()` the output is exactly silent (peak 0) from 60 ms after the stop for half a second in all three engines and both builds, no source starts, and the queued volume, pan and modulation changes on channel 16 never apply (asserted since `69e9052`; was an observation, review F11). A scratch build whose stop leaves the hits gives a peak of 1.58 (Chromium). Stop then play: the resumed note has the straight play's level (1.000x) and hard-left pan in all three engines and both builds.

## 4. OfflineAudioContext (decision and evidence)

**Decision.** Direct scheduling with explicit times is the supported offline mode. `playMIDI()` on an `OfflineAudioContext` throws an `Error` whose `code` and `message` are `AUDIO_CONTEXT_OFFLINE` before any change. Installing an offline context stops MIDI playback. On an offline context the realtime interval does nothing (no pruning, no sequencing), `send()` never calls `resume()`, and `resume()` resolves at once. `stopMIDI()`, `locateMIDI()`, `allSoundOff()` and `dispose()` work; the caller's context is never closed.

**Why not a supported `playMIDI` mode.** The sequencer schedules on a 60 ms wall-clock timer up to 0.2 s ahead of `currentTime`. An offline render advances `currentTime` far faster than wall-clock time, so before the render the sequencer can schedule only the events due in the first 0.2 s, and what it schedules during or after the render lands late or after the end. Supporting it would mean scheduling the whole song up front, which also meets `_limitVoices` (§10) and loops that never end. An explicit error is the defined, testable behavior D-018 allows.

**Evidence** (`scratch/offline-probe.js`, `logs/offline/<engine>-<build>.json`; base = `e5866e1`, T4 = this branch's source at `2efea05`; later commits do not change these paths). P: a 16-note song (one note every 0.25 s) played with `playMIDI()` on a 6 s `OfflineAudioContext`, rendered after 0, 0 and 400 ms. D: 40 notes scheduled at explicit times on a 20 s context (quality 1, reverb off), rendered three times with the interval left running.

**Voices** (review F7, documented, not changed): before rendering, `currentTime` is 0, so `_limitVoices` steals by count and stops a stolen note at time 0; more than `voices` notes on one offline context lose the earliest (the reviewer rendered 64 of 100). The README tells offline renderers to call `setVoices()` with at least the number of notes.

The offline spec (§8) asserts this in all three engines on both builds: melodic renders of 40 s of audio (over 1.3 s of wall time, so the old interval would have pruned during them) identical three times with the interval running; the error; the realtime context the constructor created is closed when an offline context replaces it; a gain of 0.5 or 0 at an injected destination halves or silences the output; zero rejections. A scratch build without the offline skip fails it (3.75e-3, Chromium). T6's render pages no longer need to stop the interval (a T6 phase-B item).

**Cost.** With no pruning, every scheduled voice's oscillators run to the end of the render (released voices decay toward silence instead of being cut at about 3 % amplitude 3.5·r after note-off). Renders take longer: 2.4 s instead of 0.84 s for the spec's 40 s Chromium render.

**Suspended and closed realtime contexts.** A suspended context accepts notes and `playMIDI()`; its clock does not move, so playback reports `play: 1` with `curTick` held until the context runs (T6 §5, T9A §2.3). `send()` asks it to resume at most once per context and task; `resume()` from a gesture starts it. Without a gesture, `resume()` stays pending in all three engines (start spec, `timer-resume`). A context closed by its owner: `resume()` rejects `AUDIO_CONTEXT_CLOSED` (start spec), `send()` never asks it, and `dispose()` does not close it again.

## 5. Engine findings and trace identity

**Chromium keeps an oscillator disconnected right after `stop()`.** `scratch/ended-probe.js` (`logs/ended-probe.txt`): in Chromium 153 an `OscillatorNode` that is stopped and disconnected in the same task never dispatches `ended` (Firefox and WebKit do), so the engine keeps it. `2efea05` disconnected pruned voices at once, and the dispose spec caught pruned oscillators that never ended. So routes are released from the `ended` handler (`7335492`), and stopped voices wait in `_gone` for it. The base build shows a related Chromium effect: the warm-up voice, pruned by a load in the context's first render quantum, can stay un-ended (`scratch/prune-probe.js`); `_gone` lets `dispose()` reach such voices.

**A wrong turn, corrected.** The first offline spec run showed a 1.13e-5 render-to-render difference in WebKit, and `040f123` stopped the `ended` handlers from disconnecting anything during offline renders, on the theory that a mid-render disconnection changed the mix's summation order. The theory did not hold: the difference persisted, it also occurs on the base build with its interval stopped (`scratch/webkit-repeat-probe.js`, `logs/webkit-repeat.txt`: quality-1 drums at the matrix seed, about one render in eight), and a scratch build that disconnects during renders shows the same variation as one that does not, in WebKit and Chromium (`logs/offline-disconnect-probe.txt`, eight renders each). `e4d700f` makes the handlers uniform again. What `040f123` got right stays: a teardown disconnects an offline context's graph at once, because an offline context dispatches no `ended` events after its render. The offline spec's repeatability check uses melodic notes (the voices the interval used to prune); T6's render spec reconciles the WebKit drum variation.

**Trace identity.** Default construction, loads and playback make upstream's WebAudio calls: pruning adds no call (routes are released from `ended`, which the mock never fires), and loads stop as upstream (§3). `tests/harness.js` (additive) gains a mock `close()` and the environment's `timers`; `FORK_PATCHES` is back to the tempo patch alone (`db5f730` removed the two percussion patches that `6967a71` had added while all-sound-off still stopped drums).

## 10. Risks and decisions

1. **Size** (§9): +10.2 % gzip, supervisor review.
2. **`resume()` after `dispose()` rejects** (`SYNTH_DISPOSED`) instead of resolving: D-018 calls post-dispose methods "safe no-ops"; resolving would claim a running context that does not exist. Documented usage handles `resume()` rejections anyway.
3. **Lazy first use includes `loadMIDI` and `reset`** (review F5, F6; documented): necessary so no channel state is set before the graph's `reset()`.
4. **Offline voice limit** (review F7; documented, unchanged): §4. Fixing it belongs to `_limitVoices`, outside T4's scope (a T7 or follow-up candidate: count only notes that overlap the new one on an offline context).
5. **Context switch during playback** (review F8, PR #37 Codex P2; documented, pre-existing): the sequencer keeps the old context's clock, so playback on a new context waits until its clock catches up. The README says to call `stopMIDI()` first.
6. **Stop residuals** (§3): the rewind does not cross a tempo event or a loop wrap; caller-timed CC7/CC11 values stay in the stored state, as upstream.
7. **Engine-dependent releases** (§5): on a realtime context that stays open, sources stopped by `dispose()` are disconnected when they end; a suspended caller context dispatches no `ended` until it runs, so their routes stay until then.
8. **README "Properties" and "What is unchanged" lines** are true only by default and predate the `stopMIDI` and `setAudioContext` changes; T9's documentation pass should update them.
9. **T5 hook**: `loadMIDIUrl` is untouched; T5 should register an abort-and-settle function in `_pend` and check `_dead`.
10. **Process note.** At about 06:04 (local) on 2026-10-03, while stopping my own stale matrix run, I force-killed every process running a browser from `_evidence/t6-validation/ms-playwright`. A concurrent T6 run at that moment, if any, would have lost its browsers.
